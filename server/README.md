# Сервер «Учёт ИТ-отдела»

PostgreSQL + Python (Flask). Хранит данные в базе, проверяет вход и права.

---

## 1. Что нужно на сервере

| | Версия | Проверка |
|---|---|---|
| PostgreSQL | 14 и новее | `psql --version` |
| Python | 3.10 и новее | `python --version` |
| Пакеты | `flask`, `psycopg[binary]` | `pip install flask "psycopg[binary]"` |

## 2. Создание базы

Выполнить **один раз** под суперпользователем `postgres`. Пароль приложения придумайте свой —
он нигде больше не используется:

```sql
create role asset_it with login password 'ПРИДУМАЙТЕ_ПАРОЛЬ';
create database asset_it owner asset_it encoding 'UTF8' template template0;
```

Затем применить схему:

```
psql -U asset_it -h localhost -d asset_it -f schema.sql
```

## 3. Настройка

Скопировать папку `server` на сервер и создать рядом с `app.py` файл `.env`:

```
PGHOST=localhost
PGPORT=5432
PGDATABASE=asset_it
PGUSER=asset_it
PGPASSWORD=ПАРОЛЬ_ИЗ_ПУНКТА_2

HOST=0.0.0.0
PORT=8000
SECRET_KEY=любая_длинная_случайная_строка
```

`.env` содержит пароль — его нельзя выкладывать и копировать в переписку.

## 4. Запуск

```
python app.py
```

При первом запуске создаются роли и четыре заводских раздела. Учётная запись
администратора **не создаётся автоматически**: пока в базе нет ни одного логина,
страница вместо входа показывает экран первого запуска (`GET /api/login-info` →
`setup: true`), где администратор задаёт своё имя, логин и пароль (`POST /api/setup`).
Как только первая учётная запись есть, `/api/setup` отвечает `409`. Пароли остальных
выдаёт администратор: «Пользователи ИТ» → карточка → поле «Пароль». Сами сотрудники
свой пароль менять не могут. Забытый пароль администратора меняется с консоли:
`python server/reset_password.py <логин>`.

Приложение открывается в браузере: `http://адрес-сервера:8000`

## 5. Автозапуск на Windows

Чтобы сервер поднимался сам после перезагрузки — через «Планировщик заданий»:
триггер «При запуске компьютера», действие — `python.exe` с аргументом `app.py`
и рабочей папкой `server`. Запускать от учётной записи, у которой есть доступ к папке.

Для нагрузки больше десятка человек встроенный сервер Flask лучше заменить на `waitress`:

```
pip install waitress
python -m waitress --host=0.0.0.0 --port=8000 app:app
```

## Учреждения

Верхний уровень всей базы. У каждого учреждения свои разделы учёта, записи,
пользователи, подразделения, отделы, материалы, IP-пулы, ремонты, уведомления,
журнал удалений и настройки домена. Общие на всю базу только учётные записи
сотрудников ИТ, роли и единицы измерения.

**Править или только смотреть — решает роль**, по каждому разделу отдельно (см. «Права
доступа»). Галочки «разрешено редактирование» у сотрудника больше нет (с 02.10.2026):
колонка `staff.can_edit` осталась в базе, но не читается.

Роли общие на всю базу, а разделы у каждого учреждения свои (`<учреждение>_equipment`),
поэтому `reg_level()` ищет уровень и по исходному имени раздела — иначе роль,
настроенная на первом учреждении, не работала бы во втором.

поэтому `reg_level()` ищет уровень и по исходному имени раздела — иначе роль,
настроенная на первом учреждении, не работала бы во втором.

**Сотрудник ИТ обслуживает одно учреждение** — поле `staff.org_id`, задаётся в его
карточке. Право `org.manage` — создание учреждений, перевод сотрудников и сводка по
всем сразу. У кого есть `admin`, тот видит все учреждения независимо от своего поля.

Текущее учреждение хранится в cookie `asset_it_org`, но **проверяется на сервере**
при каждом запросе (`current_org()`): подмена cookie не даёт ничего — вернётся
первое доступное. Переключение — `POST /api/org/select`, чужое учреждение даёт 403.

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/api/org/select` | переключиться на другое учреждение |
| POST | `/api/orgs` | создать или изменить (право `org.manage`) |
| POST | `/api/orgs/delete` | удалить пустое учреждение |
| GET/POST | `/api/orgs/access` | кто к каким учреждениям допущен |
| GET | `/api/overview` | сводка по всем учреждениям сразу |
| GET | `/api/cross` | записи, ремонты, уведомления и удаления всех учреждений |

`/api/cross` — отдельный запрос, а не расширение `/api/state`: состояние приложения
остаётся строго в рамках одного учреждения, иначе правка записей стала бы опасной —
непонятно, в чьи данные пишем. Администратор выбирает область просмотра на дашборде,
в ремонтах, уведомлениях и журнале удалений: только своё, конкретное или все сразу.

**Самое опасное место — `sync_table`.** Он стирает всё, чего нет в присланном
списке, а клиент присылает только своё учреждение. Каждый вызов поэтому идёт со
`scope`: `org_id = %s` для своих таблиц, `registry_id = any(...)` для дерева
разделов, `supply_id = any(...)` для приходов и выдач. Без этого сохранение в одном
учреждении снесло бы справочники соседнего.

## Опрос сети

Модуль `netscan.py` обходит адреса и запоминает, когда каждый последний раз отвечал.
Сначала обычный `ping`; тем, кто промолчал, — TCP-стук в 445 и 3389: у машин с
включённым брандмауэром Windows ICMP закрыт, а общий доступ и удалённый рабочий стол
отвечают. Порядок важен и по времени: обход /24 пингом — около двух секунд,
перебор портов по мёртвым адресам — больше десяти, поэтому TCP только для молчунов.

Нагрузка на сеть пренебрежимая: 254 адреса — примерно 37 КБ трафика, при обходе
раз в 15 минут это около 0,04 КБ/с.

По умолчанию опрашиваются только занятые адреса (значения вида IPv4 в характеристиках
записей); галочка «весь диапазон пулов» добавляет к ним все адреса описанных пулов.
Расписание крутится в фоновом потоке (`start_netscan()`), настройки перечитываются
перед каждым кругом — включение и смена интервала подхватываются без перезапуска.

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/netscan` | настройки, сводка прошлого обхода, число целей |
| POST | `/api/netscan` | сохранить настройки |
| POST | `/api/netscan/run` | обойти адреса прямо сейчас |

Требуют права `ip.manage`. Результат лежит в таблице `ip_status` и приходит клиенту
в составе `/api/state` как `cfg.netStatus`.

## Active Directory

Пользователи, подразделения и отделы берутся из домена по LDAP — модуль `adsync.py`,
библиотека `ldap3`. В выборку попадают только те учётные записи, у которых в
атрибуте-признаке (по умолчанию `employeeType`) стоит условленное значение
(по умолчанию `ok`): кто попадёт в учёт, решает администратор домена, не трогая
приложение.

| Вкладка в AD | Атрибут | Куда |
|---|---|---|
| Общие | `givenName`, `initials`, `sn` | ФИО — «Фамилия Имя Инициалы» |
| Общие | `telephoneNumber` | телефон |
| Общие | `mail` | почта |
| Организация | `title` | должность |
| Организация | `department` | отдел |
| Организация | `company` | подразделение |

Отделы и подразделения, которых ещё нет, заводятся автоматически (поиск по названию
без учёта регистра и лишних пробелов). **Ничего не удаляется**: сотрудник, пропавший
из выборки домена, остаётся в справочнике — за ним может числиться техника.

Повторный запуск не плодит дублей: запись ищется сначала по `objectGUID`
(переживает переименование), затем по почте, затем по ФИО.

Настройки — две вкладки раздела «LDAP»:

- **Подключение LDAP** — одно на всё, `setting.ldap`: сервер, порт, режим
  (`plain` / `starttls` / `ldaps`), Base DN, User Search Base, служебная учётная
  запись и пароль, таймауты подключения и операции, «Использовать конфигурацию LDAP».
  Итог последней проверки — `setting.ldap_status`. Пароль служебной учётки
  **никогда не отдаётся в браузер** — пустое поле при сохранении значит «оставить прежний».
  Это же подключение даёт вход: пользователь ИТ с источником LDAP входит доменным
  паролем, пока подключение включено. Кто входит — решает администратор, добавляя
  людей в «Пользователи ИТ».
- **Загрузка сотрудников** — у каждого учреждения своя, `org_setting.ldap`:
  подразделение AD, признак, отключённые, вложенные OU.

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/ldap/conn` | подключение без пароля и итог последней проверки |
| POST | `/api/ldap/conn` | сохранить подключение (только администратор) |
| POST | `/api/ldap/conn/test` | подключиться, войти служебной учёткой, прочитать Base DN |
| POST | `/api/ldap/login-test` | проверить вход сотрудника доменным логином и паролем (только администратор) |
| GET | `/api/ldap/users?q=` | подсказки для «Пользователей ИТ»: люди из AD по логину, ФИО, почте (`staff.manage`) |
| GET | `/api/persons/<id>/requests` | заявки на сотрудника из программы «Заявки ИТ» и его полномочия (см. `server/zayavki.py`) |
| GET | `/api/ldap` | настройки загрузки учреждения и сводка прошлой загрузки |
| POST | `/api/ldap` | сохранить настройки загрузки |
| POST | `/api/ldap/test` | подключиться и показать первые пять человек |
| POST | `/api/ldap/sync` | перенести выборку в справочник |

Загрузка (`/api/ldap*` без `/conn`, `/users` и `/login-test`) требует права **`ad.sync`** — его можно выдать через роль, не раздавая
администраторских прав. Сама загрузка требует ещё и разрешения на редактирование.

**Учреждение-получатель передаётся явно** (`orgId` в запросе). Настройки домена у
каждого учреждения свои, поэтому выбор на экране — одновременно и «чьи настройки
показываем», и «куда попадут люди». Чужое учреждение не отдаётся: `target_org()`
сверяет его со списком доступных, как и везде.

## Журнал удалений

Удалённая карточка исчезает из учёта, но в таблице `deletion` остаётся её снимок:
кто удалил, когда, зачем, и всё, что было в карточке, — характеристики и вся история
(её иначе не сохранить: `item_history` уходит по cascade вместе с записью).

Снимок собирает сервер из своих же данных: клиент присылает только причину, и без неё
`/api/items/delete` отвечает `400 reason_required`. Из журнала ничего нельзя удалить
через интерфейс — на то он и журнал.

## Права доступа

Права выдаются **ролям**, роль назначается сотруднику. У роли две части.

**Таблица доступа** (`role.reg_access`) — уровень по каждой строке:

| Строка | Уровни | Что даёт правка |
|---|---|---|
| каждый раздел учёта | просмотр / редактирование | всё внутри раздела: записи, категории, подкатегории, типы, характеристики, наборы, ремонт, списание; у «Расходных материалов» — приход и выдача |
| `@ip` IP-адреса | просмотр / редактирование | диапазоны (пулы), резерв, проверка сети — код `ip.edit` |
| `@docs` Приходные накладные | просмотр / редактирование | загрузка и разбор — `docs.edit` |
| `@transfers` Накладные по передаче | просмотр / редактирование | передача техники из карточки — `transfers.edit` |
| `@employees`, `@warehouses`, `@divisions`, `@departments`, `@places`, `@models` | нет / просмотр / редактирование | правка справочника — `<код>.edit` |
| `@acttpl` Шаблоны актов | нет / просмотр / редактирование | по умолчанию **закрыт** |

Разделы учёта видят все: «нет доступа» для них значит просмотр. Справочник без
просмотра не показывается в меню; на просмотре в нём ничего не нажимается. Из строк
с «@» `perms_of()` выводит коды `<код>.view` / `<код>.edit` (`AREAS` в `app.py`),
проверки по коду остаются простыми. IP-адрес у записи меняется из карточки записи —
для этого достаточно правки её раздела, `ip.edit` не нужен.

**Галочки** (`role.perms`) — закрытые страницы и то, что шире одного учреждения:

| Код | Что разрешает |
|---|---|
| `admin` | полный доступ, включая админ-панель |
| `staff.view` / `staff.manage` | пользователи ИТ и роли: просмотр / правка |
| `ad.view` / `ad.sync` | LDAP: просмотр / настройки и загрузка |
| `org.manage` | учреждения: создание, правка, перевод пользователей ИТ |
| `org.viewall` / `org.editall` | все учреждения: просмотр / правка учёта в любом |
| `deletions.view` / `deletions.manage` | журнал удалений: просмотр / удаление записей |

Старые галочки (`ledger.edit`, `registry.manage`, `ip.manage`, `docs.scan`, `supply.*`,
`repair.*`, `item.writeoff`, `users.manage`, `dict.edit`) при первом запуске переносятся
в таблицу доступа (`migrate_roles()`, отметка `setting.perm_model`) так, чтобы никто не
потерял того, что мог.

Заводские роли: Администратор, Мастер, Сотрудник ИТ, Только просмотр. Их можно менять,
кроме удаления, и создавать свои.

## Проверка доступа

Ограничения стоят **на сервере**, а не только в интерфейсе. Проверено:

```
наблюдатель видит: разделов=1 записей=1 прав=0
наблюдатель пишет: item=403 delete=403 roles=403 staff=403
после попыток: справочники не изменились
смена роли на другой раздел → видит только его
```

## API

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/login` | вход, ставит httpOnly-cookie |
| POST | `/api/logout` | выход |
| GET | `/api/state` | всё состояние и сведения о себе |
| POST | `/api/cfg` | сохранение справочников (по правам) |
| POST | `/api/items` | сохранение записей учёта |
| POST | `/api/items/delete` | удаление записей; **требует `reason`**, пишет журнал |
| GET | `/api/deletions` | журнал удалений (право `deletions.view`) |
| POST | `/api/staff`, `/api/staff/delete` | учётные записи сотрудников ИТ |
| POST | `/api/roles`, `/api/roles/delete` | роли и права |
| POST | `/api/docs/upload`, `/api/docs/apply`, `/api/docs/reopen`, `/api/docs/delete` | приходные накладные: приём файла, заведение записей, повторное открытие (админ), удаление с причиной |
| GET | `/api/docs`, `/api/docs/<id>/file` | список приходных накладных и сам файл |
| POST | `/api/transfer` | передача единицы на другой склад (`multipart`: `itemId`, `toWh`, `note`, `file`) |
| GET | `/api/transfers`, `/api/transfers/<id>/file` | накладные по передаче (обоих учреждений) и их файлы |
| POST | `/api/transfers/delete` | удалить запись о передаче — админ, с причиной, след в журнале удалений |
| GET | `/api/warehouses/all` | склады всех учреждений — выбор получателя при передаче |
| POST/GET | `/api/models/<id>/photo`, `POST …/photo/delete` | фотография модели (админ загружает, все смотрят) |

Пароли хранятся как `scrypt`-хеш с солью, в открытом виде не сохраняются нигде.

Номер записи: **7 цифр — номенклатурный** (одинаковые единицы получают хвост `/2`, `/3`…
на сервере), **10 цифр — инвентарный**. Другая длина отклоняется с пояснением (`bad_inv`).
