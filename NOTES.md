# Учёт ИТ-отдела — рабочие заметки

Состояние на **15.09.2026**. Приложение из двух частей:

- `it-inventory.html` — интерфейс (HTML + CSS + JavaScript в одном файле, без сборки);
- `server/` — Flask + PostgreSQL: хранение, вход по логину, права.

**Файл больше не открывается двойным кликом** — данные лежат в базе, нужен запущенный
сервер: `python server/app.py`, затем `http://адрес-сервера:8000`.

---

## 1. Как это работает

Сервер отдаёт `it-inventory.html` по адресу `/` и обслуживает `/api/...`. Браузер при
старте зовёт `GET /api/state`: не авторизован — показывается экран входа, иначе приходит
всё состояние (`cfg` + `items` + `me` с правами) и рисуется интерфейс.

Формат `cfg` и `items` остался прежним — сервер собирает его из таблиц и раскладывает
обратно. Поэтому вся логика интерфейса не менялась при переезде на базу.

| Что | Куда уходит |
|---|---|
| справочники (`saveCfg`) | `POST /api/cfg` — сервер пишет только то, на что есть право |
| записи (`saveItem/saveItems`) | `POST /api/items` |
| удаление записей | `POST /api/items/delete` |
| сотрудники ИТ и роли | `POST /api/staff`, `/api/roles` — отдельно от `cfg` |

Сессия — httpOnly-cookie на 30 дней. При 401 на любом запросе (кроме самой формы входа)
интерфейс сам показывает экран входа.

## 2. Структура данных

Всё, кроме самих записей, лежит в одном объекте `cfg`:

```
cfg.registries    [{id, name, icon, kind:"assets"|"supplies", builtin, statuses:[],
                    layout:{subs, specs, presets, dash}}]
cfg.categories    [{id, name, registryId}]
cfg.subcategories [{id, name, categoryId, registryId}]
cfg.types         [{id, name, categoryId, subcategoryId, registryId}]
cfg.specs         [{id, name, kind, unit, options, req, uniq, opt,
                    reqStatuses:[], group, poolId,
                    subcategoryId | typeId}]
cfg.presets       [{id, name, specs:[ ...то же без привязки... ]}]   // общие для всех разделов
cfg.users         [{id, name, position, divisionId, departmentId}]
cfg.staff         [{id, name, position, isMaster, login, role}]      // сотрудники ИТ
cfg.divisions     [{id, name}]
cfg.departments   [{id, name}]
cfg.ipPools       [{id, name, prefix:"192.168.203.", from, to, note,
                    registryId, categoryId}]                          // назначение пула
cfg.ipReserved    [{id, ip, note}]
cfg.units         ["шт","компл","уп","л","мл","кг","м", ...]         // справочник единиц
cfg.supplies      [{id, name, unit, qty, note}]                      // qty = сумма приходов
cfg.receipts      [{id, supplyId, qty, date, note}]                  // журнал поступлений
cfg.issues        [{id, supplyId, userId, qty, date, note}]          // списание на людей
cfg.repairs       [{id, itemId, registryId, inv, typeName, masterId, masterName,
                    from, to, result, note, doneNote}]                // журнал ремонтов
cfg.notices       [{id, at, type, itemId, registryId, inv, typeName,
                    masterId, text, forStaffId, seen}]                // лента событий

items             [{id, registryId, inv, type, status, owner, division, department,
                    notes, specs:{specId:value}, specsNone:{specId:true},
                    masterId, statusDate, statusNote, history:[{d,t}]}]
```

**Иерархия:** Раздел учёта → Категория → Подкатегория → Тип → Запись.
Характеристики задаются на **подкатегории** (стандартные, наследуются всеми её типами)
либо на **типе** (собственные). `specsOf(typeId)` склеивает то и другое.

## 3. Экраны (боковая панель)

- **Ремонты** — отдельный экран по `cfg.repairs`: плитки (в ремонте, завершено, списано,
  среднее дней, всего), фильтры по состоянию / мастеру / разделу, поиск, выгрузка CSV
  (`exportRepairs()`), клик по строке открывает **окно ремонта** (`openRepairDlg()`) —
  там полный текст причины и выполненных работ, оттуда можно перейти в карточку
  оборудования. История ремонтов в профиле мастера ведёт туда же (`ids` вида `rp:<id>`). Незакрытые ремонты идут сверху
  и считают дни по сегодняшний день. Счётчик открытых ремонтов — в боковой панели.
- **Уведомления** — лента событий по ремонту (`notify()` из `syncRepairLog()`), счётчик
  непрочитанных в боковой панели. Клик помечает прочитанным и открывает карточку;
  список разделён на «Новые» и «Прочитанные». **Удалять уведомления нельзя** — это
  история событий, кнопки очистки нет.
  Пока общая для всех: поле `forStaffId` заполняется, но не фильтрует — станет адресной
  вместе со входом в систему.
- **Общий дашборд** — шесть плиток: Всего оборудование (*без* расходников),
  В эксплуатации, В ремонте, Материалов на складе, Списаний, Занятых IP. **Все кликабельны**
  (`openDrill()`): открывают разбивку по разделам и список позиций; у «В ремонте» колонки
  Мастер и Отправлен. Дальше таблица разделов
  (`⚙` настройки, `✕` удалить — у заводских заблокирована), разбивка по подразделениям,
  «+ Новый раздел учёта». **Настройка разделов живёт только здесь и только у админа** —
  внутри самих разделов кнопки настроек нет.
- **Разделы учёта** (Оборудование, IP-телефоны, Рации, любые созданные) — вкладки
  `Дашборд · Записи · Категории · Подкатегории · Типы · Характеристики · Наборы`.
- **Расходные материалы** — особый раздел (`kind:"supplies"`), свой экран с двумя
  вкладками: «Приход и остатки», «История поступлений» и «Выдано и установлено».
  Каждый приход — отдельная запись в `cfg.receipts` с датой; `supply.qty` пересчитывается
  из них функцией `recalcSupply()` и вручную не правится. **У него своя выгрузка**:
  `exportSupplies()` / `importSupplies()` вместо `exportCSV()` — материалы лежат в
  `cfg.supplies`, а не в `items`, поэтому общий экспорт выдавал пустой файл.
  На вкладке «Выдано» импорт скрыт, выгружается журнал списаний.
  При импорте склада «Поступило» из файла **заменяет** значение, а не прибавляется,
  чтобы выгрузка и загрузка не удваивали остаток.
- **IP-адреса** — плитки, вкладки пулов, сетка всех хостов диапазона, таблица занятых.
  Форма пулов спрятана в диалог по кнопке «⚙ Диапазоны (пулы) адресов».
- **Пользователи** — клик по строке открывает профиль (закреплённая техника + выданные
  материалы), `✎` — правка. Удалить нельзя, пока числится активная техника.
- **Сотрудники ИТ** — отдельный список с колонкой «На ремонте»; клик по строке открывает
  профиль: что сейчас в ремонте (`repairsOfMaster()`) и **история ремонтов** с датами,
  числом дней и колонкой «Причина → что сделали» (`repairsHistory()`), плюс сводка
  «всего / завершено / в среднем дней». `✎` — правка.
  Строки сводных мини-таблиц кликабельны: `miniTable(head, rows, empty, ids)` вешает
  `data-open`, а `openItemById()` закрывает диалог и открывает карточку записи. Так
  работают профиль мастера, профиль пользователя и детализация плиток дашборда. Логин и роль заполняются на будущее.
- **Подразделения**, **Отделы** — общие справочники.

## 4. Ключевые правила, которые легко сломать

1. **Обязательность характеристики зависит от статуса** (`spec.reqStatuses`).
   Пустой массив = обязательна всегда. Так поля «AD и IP» не требуются на складе.
   Проверяется функцией `specReq(sp, status)`.
2. **Группы полей** (`spec.group`) — при применении набора проставляется имя набора;
   в карточке поля идут блоками с заголовком. Кнопка «Отметить группой набора»
   проставляет группу уже существующим характеристикам по совпадению названий.
3. **Уникальность** (`spec.uniq`) считается по **одноимённым** характеристикам во всех
   разделах сразу — поэтому IP не повторится ни у ПК, ни у телефона. MAC сравнивается
   без учёта регистра и разделителей.
4. **Пулы IP**: пул знает своё назначение — раздел и, необязательно, категорию.
   `poolsForSpec()` собирает **все** подходящие: сначала явная привязка `spec.poolId`
   (если есть), затем пулы раздела с этой категорией и пулы раздела без категории.
   Явная привязка не отсекает остальные — иначе при двух подсетях на категорию выбор
   в карточке не появлялся. Поэтому одну и ту же
   характеристику «IP адрес» в разных разделах привязывать вручную не нужно.
   Если подходящих диапазонов несколько, вместо статичного префикса в поле рисуется
   выпадающий список (`data-poolsel`), смена которого переписывает `data-prefix` у input.
   Валидация ищет среди всех подходящих пулов тот, чьему префиксу отвечает адрес.
   Если у характеристики задан `poolId`, в карточке рисуется префикс
   `192.168.203.` + поле только для хоста. Валидация не пропустит чужую подсеть и хост
   вне диапазона. Поле **без** пула не примет адрес, принадлежащий чужому пулу.
5. **Статус «На складе» / «Списано»** прячет и **очищает** ответственного, подразделение
   и отдел; в историю пишется `Снято с сотрудника: ФИО, подразделение, отдел`.
   «В ремонте» — показывает выбор мастера (обязателен), дату и примечание.
   «На складе» у **новой** записи — поле «Кол-во», создаётся N копий (уникальные
   характеристики при этом должны быть пустыми).
6. **Заводские разделы** `equipment / ipphone / supplies / radio` помечаются
   `builtin:true` в `normCfg` по списку `SEED_IDS`. У них нельзя менять название,
   значок и тип, нельзя удалить. Статусы и наполнение менять можно.
7. **Наполнение раздела** (`registry.layout`) — какие вкладки и поля показывать:
   `subs` (подкатегории), `specs`, `presets`, `dash`. Выключенный `subs` скрывает
   вкладку, фильтр, поле в карточке и колонку через класс `body.nosubs` +
   `.col-sub` (класс именно на `body`, иначе не подействует на диалоги).
8. **Статусы раздела** редактируются в диалоге «Настройки раздела». Переименование
   переносится на записи раздела и на `spec.reqStatuses`; удаление статуса переводит
   записи на первый в списке. «На складе», «В ремонте», «Списано» переименовать нельзя —
   Журнал ремонтов ведётся отдельно от записи: `syncRepairLog()` открывает строку при
   переходе в «В ремонте» и закрывает при выходе, поэтому история не теряется после
   возврата в эксплуатацию и переживает удаление записи (в строке лежит снимок inv/типа).
   При возврате из ремонта карточка показывает поля «Дата возврата» и «Что сделали».
   Дни считает `daysBetween()`; у незакрытого ремонта — по сегодняшний день.
   Особые статусы нельзя переименовать —
   на их текст завязана логика карточки и плитки дашборда
   (`ST_USE` / `ST_STOCK` / `ST_REPAIR` / `ST_READY` / `ST_OFF` — все пять в `SPECIAL_ST`).
   `ST_READY` = «Готово к эксплуатации» — промежуточный статус: мастер закончил, технику
   ещё не установили. Он досеивается в статусы существующих разделов в `normCfg`, иначе
   старые конфиги его не получат. Переход в него закрывает ремонт так же, как возврат
   в эксплуатацию, и шлёт уведомление.
9. **Роли**: `isAdmin()` — единственная точка проверки. Пока входа нет, роль лежит в
   `localStorage["it_inv_role"]` и переключается кнопками внизу боковой панели
   (`admin` / `view`). Это **не защита**, а способ спрятать лишнее: любой может
   переключить обратно. Не-админу скрыты `.col-adm` (через `body.noadmin`) и кнопка
   «+ Новый раздел»; `openRegDlg()` и `deleteRegistry()` дополнительно отбивают вызов.
   Мастера назначает только админ: `f_master` и галочка `data-master` у не-админа
   заблокированы, требование выбрать мастера при «В ремонте» действует лишь для него.
10. **Тема**: `auto` / `light` / `dark`, переключатель внизу боковой панели, выбор в
   `localStorage["it_inv_theme"]`. Крошечный скрипт в `<head>` ставит `data-theme`
   до отрисовки, чтобы не было вспышки светлого на тёмной теме.
11. **`hidden` сам по себе не скрывает элемент**, если у него есть авторский `display`
   (`.row{display:flex}` перебивала атрибут, и кнопки CSV торчали на всех вкладках).
   В CSS стоит `[hidden]{display:none !important}` — не убирать. В тестах проверять
   видимость по `getBoundingClientRect().width`, а не по свойству `.hidden`.
12. **Выгрузка CSV** разная в трёх местах: `exportCSV()` — записи раздела (только вкладка
   «Записи»); каждая характеристика уходит **отдельной колонкой** (`specColumns()`):
   ОЗУ, диск, БП, ЦПУ, имя ПК, IP — чтобы в Excel их можно было фильтровать и считать.
   Одноимённые характеристики из разных подкатегорий сводятся в одну колонку
   (ключ — название + единица), значение берётся по первому заполненному id.
   Импорт читает те же колонки по названию, так что выгрузку можно править в Excel
   и заливать обратно.

   Рядом с «Экспорт CSV» стоит **«Экспорт Excel»** — тот же набор данных, но настоящий
   `.xlsx`. Книга собирается прямо в браузере: `zipStore()` пишет zip **без сжатия**
   (метод 0 — Excel такие открывает, а кода на дефлейт не нужно), `xlsxSheet()` —
   лист с объединённой шапкой «Характеристики», автофильтром, закреплённой строкой
   и шириной колонок по содержимому. Внешних библиотек нет намеренно: приложение
   должно оставаться одним файлом. Числа пишутся числами, но инвентарные номера и всё
   с ведущим нулём — текстом (`asNumber()`), иначе Excel съедает нули (`0013500`).
   Формат выбирает `expFmt`, обе кнопки зовут один `runExport()`; ragged-отчёты
   (сводка, карта пула) идут через `saveBlock()` в режиме `plain` — без фильтра и
   объединений. Проверять книгу: headless Chrome отдаёт её в base64, дальше `openpyxl`
   (`readxlsx.py`). `exportSupplies()` — склад / журнал приходов / выдачи по активной вкладке,
   `exportDashboard()` — сводный отчёт с общего дашборда (итоги, разделы, статусы,
   подразделения, отделы, материалы), `openIpExport()` — выгрузка IP-адресов с выбором
   колонок: 12 основных плюс любые характеристики по названию (`specValueByName()`
   ищет поле у записи, за которой закреплён адрес). Выбор колонок запоминается в
   `localStorage["it_inv_ipcols"]`. Импорт есть только на «Записях» и на складе.
13. **Фильтры записей** — одна компактная строка без подписей: в каждом селекте первый
   вариант уже говорит, что это («Все категории»), поэтому подписи были лишними.
   Активные фильтры подсвечиваются классом `act` (`markFilters()`), кнопка «Сбросить»
   появляется только когда что-то выбрано, счётчик найденного — в той же строке.
   Блок ужался со 191px до 30px.
14. **Единицы измерения** — не текстовое поле, а список из `cfg.units`, чтобы не плодить
   «шт»/«шт.»/«штук». Последняя опция `＋ добавить свою…` видна только админу и заводит
   новую единицу через prompt. Единицы, введённые до этого вручную, и единицы из
   импортируемых файлов подхватываются в справочник в `normCfg` / `importSupplies`.
   Название материала — `input` с `datalist` из уже заведённых: можно выбрать или
   написать новое, а при выборе известного подставляется его единица.
15. **Таблицы**: `table-layout:fixed` + `<colgroup>` в процентах, строка ровно 44px,
   текст обрезается многоточием, полное значение в `title`.
   **Пиксельные ширины колонок мешать с процентами нельзя** — ломается раскладка
   (проверено: колонка «#» в 42px раздувалась до 200px на узком окне).
   Первая колонка везде — номер строки (3.4%), нумерация пересчитывается после
   фильтрации и сортировки.

## 5. Серверная часть (сделано 15.09.2026)

Папка `server/` — PostgreSQL + Flask:

- `schema.sql` — 22 таблицы: роли, сотрудники ИТ с логинами, сессии, справочники,
  записи учёта, ремонты, расходники, уведомления.
- `app.py` — API и проверка прав; пароли хранятся как `scrypt`-хеш с солью.
- `README.md` — развёртывание на сервере, список прав, автозапуск.
- `.env` — пароль базы и настройки (в переписку и в репозиторий не попадает).

Права выдаются **ролям**, роль назначается сотруднику. Помимо списка прав у роли есть
доступ по разделам: `нет / просмотр / редактирование`. Раздел без доступа **не приходит
клиенту вовсе** — фильтрация в `load_state()`, а не в интерфейсе.

Служебные разделы закрыты не только на кнопках: `NAV_PERM` + `navAllowed()` не пускают
в «Сотрудники ИТ» и «Роли и доступ» без права `staff.manage`, в «Историю удалений» —
без `deletions.view`, а `render()` выкидывает на дашборд, если право отобрали. Раньше
мастер туда заходил, правил форму и получал отказ только при сохранении.

**Учреждения** (16.09) — верхний уровень всего. Таблица `org`, учреждение
сотрудника — поле `staff.org_id` (одно, миграция `007_staff_one_org.sql`), настройки
домена и опроса сети в `org_setting`, право `org.manage`, миграция
`006_organizations.sql`.

**Просмотр по умолчанию** (17.09). Доступ к учреждению не даёт права менять данные:
нужна галочка «Разрешено редактирование» в карточке сотрудника (`staff.can_edit`,
миграция `008_view_only_access.sql`). Проверка стоит и на сервере (`may_write()` в
`/api/cfg`, `/api/items`, `/api/items/delete` → `403 read_only`), и в интерфейсе
(`regLevel()` понижает `edit` до `view`, в боковой панели подпись «только просмотр»).
Тем, кто был заведён раньше, миграция проставила `can_edit = true`: сужать права
молча нельзя, иначе люди утром не смогут работать и не поймут почему.

Роли общие на всю базу, а разделы у каждого учреждения свои — поэтому уровень доступа
ищется и по имени без приставки учреждения (`org_plant2_equipment` → `equipment`).
Без этого роль, настроенная на первом учреждении, молча не работала бы во втором.

**Статус «На списание»** (`ST_TOOFF`, миграция `009_status_to_writeoff.sql`) — техника
ждёт решения комиссии месяцами: в эксплуатации её уже нет, а списанной называть
ещё нельзя. Ставит его любой, кто правит записи; само «Списано» по-прежнему требует
права `item.writeoff`. Владелец при этом сохраняется — комиссия может и отказать.
Миграция досеивает статус перед «Списано» во всех уже заведённых разделах, клиент
делает то же для надёжности в `normCfg()`.

**Право `org.viewall`** — «видеть все учреждения» для начальника отдела: сводка,
сквозные списки и селектор области, но без создания учреждений и без правки.
Раньше это умел только `admin`. На сервере — декоратор `need_view_all`, в интерфейсе
`me.seesAllOrgs` вместо проверки `can("org.manage")`.

Проверка `permtest.py` тогда же нашла две настоящие ошибки:
`/api/cfg` молча отвечал `200` читающему пользователю (ничего не менял, но и не
отказывал), а начальник отдела видел **пустой список разделов** — `load_state()`
считал доступные разделы напрямую по роли, минуя `reg_level()` с его правилами.

Администратор смотрит шире: селектор области на дашборде, в ремонтах, уведомлениях
и журнале удалений («только своё» / конкретное / все сразу). Данные для него приходят
отдельным запросом `/api/cross`, а не в `/api/state`: состояние приложения должно
остаться в рамках одного учреждения, иначе непонятно, в чьи данные пишет сохранение.
На широком дашборде карточки те же, что и в обычном режиме: «Разделы учёта» и
«По подразделениям», только списки общие — одноимённые разделы разных учреждений
складываются по названию. Зато в окне детализации (клик по плитке) первой колонкой
идёт **учреждение**, а сводка сверху считается по учреждениям: иначе строки разных
заводов в одном списке не различить. Карточку записи оттуда не открыть — данных
чужого учреждения в памяти браузера нет. Кнопка «+ Новый раздел учёта» в широком
режиме скрыта: непонятно, в какое учреждение он бы добавился.

Стартовый экран — «Общий дашборд» (`var nav = "dash"`), раньше открывался раздел учёта.
В списке области «Все учреждения» стоит первым пунктом. Всё существовавшее переехало в учреждение
«Основное» (`org_main`), его можно переименовать в карточке.

Разделено: разделы учёта и всё их дерево, записи, пользователи, подразделения,
отделы, наборы, материалы с приходами и выдачами, IP-пулы и резерв, состояние
адресов, ремонты, уведомления, журнал удалений. Общими остались учётные записи
сотрудников ИТ, роли и единицы измерения.

Четыре места, где легко всё сломать:

1. **`sync_table` без `scope` стирает чужое.** Клиент присылает справочники только
   своего учреждения, а функция удаляет всё, чего нет в списке. Каждый вызов теперь
   со своей областью: `org_id` для своих таблиц, `registry_id = any(...)` для
   категорий-подкатегорий-типов, `supply_id = any(...)` для приходов и выдач,
   отдельное условие для характеристик (они висят на подкатегории или типе).
2. **Текущее учреждение приходит из cookie, значит ему нельзя верить.**
   `current_org()` сверяет его со списком доступных и молча возвращает первое
   разрешённое. Проверено подменой: сотрудник с доступом к одному учреждению,
   подсунув чужой id, получает своё, а `/api/org/select` отвечает 403.
3. **`seed()` заводит учреждение раньше разделов.** На чистой установке миграция
   отрабатывает по пустой базе и учреждения не создаёт; если бы `seed()` вставил
   заводские разделы с пустым `org_id`, они не попали бы ни в одну выборку.
4. **Проверять изоляцию надо на явно выбранном учреждении.** Первый прогон
   `orgtest.py` «нашёл» нарушение изоляции, а на деле тест сам брал
   первое попавшееся учреждение: у обоих `sort = 0`, и «Завод-2» встало вперёд
   «Основного» по алфавиту.
5. **Стенд открывается не на дашборде, а на разделе учёта** (`nav = "reg"`).
   Селектор области виден только на дашборде, ремонтах, уведомлениях и удалениях,
   поэтому сценарий проверки должен сначала нажать «Общий дашборд» — иначе у списка
   не окажется вариантов и проверка «не увидит» работающую функцию. Полчаса ушло на
   эту ошибку в тесте, а не в коде.
6. **Ошибки внутри `.then()` не ловит `window.onerror`.** Пока к цепочке
   `loadCross().then(renderAll)` не был приписан `.catch`, сбой отрисовки просто
   исчезал: интерфейс оставался в прежнем виде и ничего не сообщал.

**Опрос сети** (16.09). Сервер обходит адреса и показывает в разделе «IP-адреса»,
кто сейчас в сети и когда отвечал последний раз (`server/netscan.py`, таблица
`ip_status`, миграция `005_ip_status.sql`, право `ip.manage`).

Мерил перед тем, как делать: обход 254 адресов занимает 2 с при 64 потоках и
около 37 КБ трафика — раз в 15 минут это 0,04 КБ/с, то есть нагрузки нет вовсе.
Зато перебор TCP-портов по тем же 254 адресам — 12 с, поэтому он только для тех,
кто не ответил на ping. Это не оптимизация ради оптимизации: **у машин с включённым
брандмауэром Windows ICMP закрыт**, и без стука в 445/3389 половина живых компьютеров
показывалась бы выключенной.

Три места, где легко ошибиться:
`normCfg()` собирает объект из белого списка полей — новый `netStatus` пришлось
добавить туда явно, иначе он молча терялся и колонка показывала прочерки.
Фоновый поток надо поднимать и в `serve.py`, а не только в `__main__` у `app.py`:
на сервере работает waitress, и расписание иначе не запускалось бы.
Настройки перечитываются перед каждым кругом, поэтому включение и смена интервала
не требуют перезапуска.

**Active Directory** (16.09). Справочник пользователей заполняется из домена:
модуль `server/adsync.py` на `ldap3`, экран «Active Directory» в интерфейсе,
права — `users.manage`. Признак отбора задаёт администратор домена в атрибуте
`employeeType` (значение и сам атрибут настраиваются). ФИО собирается как
«Фамилия Имя Инициалы» из `sn` + `givenName` + `initials`; телефон и почта —
новые поля `person.phone` / `person.email` (миграция `004_ldap_users.sql`).
Подразделение берётся из `company`, отдел — из `department`, и оба заводятся сами,
если их ещё нет.

Поле «Только подразделение AD (OU)» ограничивает поиск веткой дерева: можно указать
полный DN, просто имя подразделения или путь через «/» («Заводы/Завод-1» →
`OU=Завод-1,OU=Заводы,<база>`). Галочка «вместе с вложенными OU» переключает область
поиска между SUBTREE и LEVEL. Раньше тянулось всё дерево домена.

Три решения, которые стоит помнить:
`objectGUID` пишем в `person.ad_guid` — по нему запись находится после переименования
в домене, иначе повторная загрузка заводила бы второго человека. Отключённые учётки
отсеиваются **в коде**, а не фильтром LDAP: битовая проверка
`userAccountControl:1.2.840.113556.1.4.803:=2` есть не в каждом каталоге и её не
понимает мок ldap3. Пароль служебной учётки лежит в `setting` и наружу не уходит —
`public_config()` его вырезает, пустое поле значит «не менять».

Проверять без домена: `adtest.py` поднимает каталог в памяти
(`ldap3` MOCK_SYNC) и гоняет настоящий код разбора и переноса, а изменения в базе
откатывает. В моке нужно класть `objectCategory: "person"` строкой — настоящий AD
разворачивает это в DN схемы сам, поддельный каталог так не умеет.

**Журнал удалений** (16.09, после того как из базы пропала запись и выяснить это было
негде). Удаление записи теперь спрашивает причину: кнопка «Удалить» в окне `dlgDelAsk`
недоступна, пока не написано хотя бы три символа, а сервер без `reason` отвечает
`400 reason_required` — проверка не только в интерфейсе. Перед удалением сервер
складывает в таблицу `deletion` снимок карточки: кто, когда, зачем, раздел, категория,
тип, статус, ответственный, примечание, все характеристики и вся история записи.
Историю иначе не сохранить — `item_history` уходит по cascade. Снимок собирается
на сервере из его же данных, присланному клиентом не верим.

**Пакет для установки на сервер без интернета** — `dist/asset-it-server/` и рядом
`asset-it-server.zip` (16.09). Внутри: страница, `server/`, папка `wheels` со всеми
зависимостями (flask, psycopg[binary], waitress — колёса cp314 win_amd64) и .bat-файлы.
`install.bat` создаёт `.venv`, ставит колёса через `pip --no-index --find-links wheels`
и зовёт `server/setup_db.py`: тот заводит пользователя и базу, генерирует пароль и
`SECRET_KEY`, пишет `.env` и применяет `schema.sql`. Повторный запуск безопасен —
пароль из существующего `.env` не перезаписывается, иначе слетели бы входы.

Рабочий сервер поднимает `server/serve.py` на **waitress**, а не отладочным сервером
Flask. `start.bat` запускает его с `-u`: без этого вывод копится в буфере и пароль
первого входа не виден. Автозапуск — `autostart-install.bat`, порт —
`open-firewall.bat`, копии базы — `backup-db.bat`, остановка — `stop.bat`.

**Задача планировщика запускает `pythonw.exe` напрямую.** Сначала она вызывала
посредника `start-hidden.vbs`, который стартовал процесс и тут же завершался: задача
считалась выполненной, процесс жил сам по себе, и `schtasks /end` останавливать было
уже нечего — сервер продолжал отвечать. Проверено: с прямым запуском `/end`
действительно снимает процесс и освобождает порт. Файл `start-hidden.vbs` удалён.
`stop.bat` на всякий случай делает и то, и другое: гасит задачу и снимает процесс,
найденный по порту из `server/.env`.

Кодировка .bat — отдельная история, проверенная тремя прогонами. Сначала писал их
в **cp866**: в консоли верно, а в редакторе сплошные кракозябры — а эти файлы человек
открывает и читает. **UTF-8 с BOM нельзя**: cmd принимает BOM за часть первой команды
(`"﻿@echo" не является внутренней или внешней командой`), `echo off` не срабатывает и
дальше всё сыплется. Итог: **UTF-8 без BOM**, второй строкой `chcp 65001 >nul`, третьей
`set PYTHONIOENCODING=utf-8` — иначе Python при выводе в файл берёт cp1251 и расходится
с консолью. Заодно в питоновских скриптах стоит `sys.stdout.reconfigure(errors="replace")`,
чтобы прямой запуск без `chcp` не падал на символах вроде `─`.

Внутри `echo` нельзя `<`, `>` и **круглые скобки**: первые два cmd считает
перенаправлением («Не удается найти указанный файл»), а `)` закрывает блок `if` раньше
времени — строка `Установите Python 3.14 (64 бита) и поставьте галочку` роняла установку
с `и was unexpected at this time`. В генераторе `mkbat2.py` стоит проверка,
которая ищет такие строки.

Экран «История удалений» (`v-dels`, `renderDels()`, данные — `/api/deletions`) только
показывает: ни строки добавить, ни убрать. Клик по строке открывает `dlgDelInfo` —
карточку удалённой записи целиком. Есть поиск, фильтры по сотруднику и разделу,
выгрузка в CSV и Excel. Удаление раздела пишет в журнал каждую его запись с причиной
«Удалён раздел «…»» — отдельно причину не спрашиваем, она уже в подтверждении.

**База одна — `asset_it`** (настройки в `server/.env`). 16.09 пользователь так и решил:
отдельная тестовая база не нужна, чтобы при переносе на сервер не было путаницы,
`asset_it_test` удалена.

Проверки интерфейса поэтому идут **без базы**: копия страницы с подменённым `fetch`,
состояние — заглушка (`stub.py`), открывается как файл в headless Chrome.
Если проверка всё-таки требует сервера, в рабочей базе после неё ничего не должно
остаться: 15.09 так в неё попали тестовые записи INV-1, SRV-1 и роль `role_look`.

Автор каждого события истории и поле «кто менял последним» проставляет **сервер**
(`save_items`): клиент присылает только новые события в `historyAdd`, готовую историю
из него не берут — иначе автора можно было бы подделать.

Интерфейс подключён к серверу: экран входа, блок пользователя в боковой панели
(имя, роль, «Выйти»), экран **«Роли и доступ»** — галочки прав и уровень доступа
к каждому разделу. Свой пароль сотрудник сменить не может: `/api/password` удалён,
пароли выдаёт администратор в карточке сотрудника ИТ (поле «Пароль», пустое — не менять).
Боковая панель не прокручивается целиком: прокрутку берёт на себя только список
разделов `.side-nav`, причём без видимой полосы — подвал с темой и пользователем
всегда прижат к низу. Сотрудники ИТ теперь учётные записи: логин, пароль, роль, признак
«доступ разрешён».

Права в интерфейсе (`applyPerms()`) прячут кнопки, карточка в разделе «только просмотр»
открывается с заблокированными полями и без кнопок сохранения. Статусы «В ремонте»,
«Готово к эксплуатации» и «Списано» отключаются в списке, если нет `repair.send`,
`repair.close` или `item.writeoff`. **Настоящая проверка — на сервере**, интерфейс только
не показывает лишнего.

## 7. Как проверять изменения

Сборки нет, поэтому проверка — прогон настоящей страницы в headless-браузере:

```bash
# 1) синтаксис JS (JScript строг к ES5, .catch/.delete нужно временно переименовать)
cscript //Nologo //E:JScript parse-test.js

# 2) интеграционный прогон: скрипт-сценарий дописывается в копию страницы,
#    результат складывается в document.title и читается из dump-dom
chrome --headless=new --disable-gpu --window-size=1440,900 \
       --virtual-time-budget=9000 --dump-dom file:///.../test.html | grep '<title>'
```

Сценарии кликают по реальным кнопкам (`side()`, `rt()`, `card()`), поэтому ловят и
логику, и вёрстку. Обязательно проверять `overflowX` (горизонтальной прокрутки быть
не должно) и совпадение числа `<col>` / `<th>` / ячеек во всех таблицах.

Перед правкой — копия файла в отдельную папку. Предыдущие копии лежали во временном
каталоге сессии (`…\Temp\…\it-inventory.backup*.html`) и
**после перезагрузки могут пропасть** — если нужна история, копировать рядом с проектом.
