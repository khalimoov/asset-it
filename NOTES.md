# Учёт ИТ-отдела — рабочие заметки

Состояние на **21.09.2026**. Приложение из двух частей:

- `it-inventory.html` — интерфейс (HTML + CSS + JavaScript в одном файле, без сборки);
- `server/` — Flask + PostgreSQL: хранение, вход по логину, права.

**Файл больше не открывается двойным кликом** — данные лежат в базе, нужен запущенный
сервер: `python server/app.py`, затем `http://адрес-сервера:8000`.

---

## 1. Как это работает

Сервер отдаёт `it-inventory.html` по адресу `/` и обслуживает `/api/...`. Браузер при
старте зовёт `GET /api/state`: не авторизован — показывается экран входа, иначе приходит
всё состояние (`cfg` + `items` + `me` с правами) и рисуется интерфейс.

Формат `cfg` и `items` остался прежним — сервер собирает его из таблиц и раскладывает
обратно. Поэтому вся логика интерфейса не менялась при переезде на базу.

| Что | Куда уходит |
|---|---|
| справочники (`saveCfg`) | `POST /api/cfg` — сервер пишет только то, на что есть право |
| записи (`saveItem/saveItems`) | `POST /api/items` |
| удаление записей | `POST /api/items/delete` |
| сотрудники ИТ и роли | `POST /api/staff`, `/api/roles` — отдельно от `cfg` |

Сессия — httpOnly-cookie на 30 дней. При 401 на любом запросе (кроме самой формы входа)
интерфейс сам показывает экран входа.

## 2. Структура данных

Всё, кроме самих записей, лежит в одном объекте `cfg`:

```
cfg.registries    [{id, name, icon, kind:"assets"|"supplies", builtin, statuses:[],
                    layout:{subs, specs, presets, dash}}]
cfg.categories    [{id, name, registryId}]
cfg.subcategories [{id, name, categoryId, registryId}]
cfg.types         [{id, name, categoryId, subcategoryId, registryId}]
cfg.specs         [{id, name, kind, unit, options, req, uniq, opt,
                    reqStatuses:[], group, poolId,
                    subcategoryId | typeId}]
cfg.presets       [{id, name, specs:[ ...то же без привязки... ]}]   // общие для всех разделов
cfg.users         [{id, name, position, divisionId, departmentId}]
cfg.staff         [{id, name, position, isMaster, login, role}]      // сотрудники ИТ
cfg.divisions     [{id, name}]
cfg.departments   [{id, name}]
cfg.ipPools       [{id, name, prefix:"192.168.203.", from, to, note,
                    registryId, categoryId}]                          // назначение пула
cfg.ipReserved    [{id, ip, note}]
cfg.units         ["шт","компл","уп","л","мл","кг","м", ...]         // справочник единиц
cfg.supplies      [{id, name, unit, qty, note}]                      // qty = сумма приходов
cfg.receipts      [{id, supplyId, qty, date, note}]                  // журнал поступлений
cfg.issues        [{id, supplyId, userId | itemId, qty, date, note}] // списание на людей или в технику
cfg.repairs       [{id, itemId, registryId, inv, typeName, masterId, masterName,
                    from, to, result, note, doneNote}]                // журнал ремонтов
cfg.notices       [{id, at, type, itemId, registryId, inv, typeName,
                    masterId, text, forStaffId, seen}]                // лента событий

items             [{id, registryId, inv, type, status, owner, division, department,
                    notes, specs:{specId:value}, specsNone:{specId:true},
                    masterId, statusDate, statusNote, history:[{d,t}]}]
```

**Иерархия:** Раздел учёта → Категория → Подкатегория → Тип → Запись.
Характеристики задаются на **подкатегории** (стандартные, наследуются всеми её типами)
либо на **типе** (собственные). `specsOf(typeId)` склеивает то и другое.

## 3. Экраны (боковая панель)

- **Ремонты** — отдельный экран по `cfg.repairs`: плитки (в ремонте, завершено, списано,
  среднее дней, всего), фильтры по состоянию / мастеру / разделу, поиск, выгрузка CSV
  (`exportRepairs()`), клик по строке открывает **окно ремонта** (`openRepairDlg()`) —
  там полный текст причины и выполненных работ, оттуда можно перейти в карточку
  оборудования. История ремонтов в профиле мастера ведёт туда же (`ids` вида `rp:<id>`). Незакрытые ремонты идут сверху
  и считают дни по сегодняшний день. Счётчик открытых ремонтов — в боковой панели.
- **Уведомления** — лента событий по ремонту (`notify()` из `syncRepairLog()`), счётчик
  непрочитанных в боковой панели. Клик помечает прочитанным и открывает карточку;
  список разделён на «Новые» и «Прочитанные». **Удалять уведомления нельзя** — это
  история событий, кнопки очистки нет.
  Пока общая для всех: поле `forStaffId` заполняется, но не фильтрует — станет адресной
  вместе со входом в систему.
- **Общий дашборд** — шесть плиток: Всего оборудование (*без* расходников),
  В эксплуатации, В ремонте, Материалов на складе, Списаний, Занятых IP. **Все кликабельны**
  (`openDrill()`): открывают разбивку по разделам и список позиций; у «В ремонте» колонки
  Мастер и Отправлен. Дальше таблица разделов
  (`⚙` настройки, `✕` удалить — у заводских заблокирована), разбивка по подразделениям,
  «+ Новый раздел учёта». **Строки обеих таблиц тоже открывают карточку** (`openDrill("reg:<id>")`,
  `"div:<id>"`, в широком режиме — `"regn:<название>"` / `"divn:<название>"`): статусы чипами,
  сводка по разделам, список позиций; у раздела внизу кнопка «Открыть раздел» (`btnDrillGo`). **Настройка разделов живёт только здесь и только у админа** —
  внутри самих разделов кнопки настроек нет.
- **Разделы учёта** (Оборудование, IP-телефоны, Рации, любые созданные) — вкладки
  `Дашборд · Записи · Категории · Подкатегории · Типы · Характеристики · Наборы`.
- **Расходные материалы** — особый раздел (`kind:"supplies"`), свой экран с тремя
  вкладками: «Таблица факт» (остатки + выдачи), «Таблица склада» и «История поступлений».
  Каждый приход — отдельная запись в `cfg.receipts` с датой; `supply.qty` пересчитывается
  из них функцией `recalcSupply()` и вручную не правится. **У него своя выгрузка**:
  `exportSupplies()` / `importSupplies()` вместо `exportCSV()` — материалы лежат в
  `cfg.supplies`, а не в `items`, поэтому общий экспорт выдавал пустой файл.
  На вкладке «Выдано» импорт скрыт, выгружается журнал списаний.
  При импорте склада «Поступило» из файла **заменяет** значение, а не прибавляется,
  чтобы выгрузка и загрузка не удваивали остаток.
- **IP-адреса** — плитки, вкладки пулов, сетка всех хостов диапазона, таблица занятых.
  Форма пулов спрятана в диалог по кнопке «⚙ Диапазоны (пулы) адресов».
- **Пользователи** — клик по строке открывает профиль (закреплённая техника + выданные
  материалы), `✎` — правка. Удалить нельзя, пока числится активная техника.
- **Сотрудники ИТ** — отдельный список с колонкой «На ремонте»; клик по строке открывает
  профиль: что сейчас в ремонте (`repairsOfMaster()`) и **история ремонтов** с датами,
  числом дней и колонкой «Причина → что сделали» (`repairsHistory()`), плюс сводка
  «всего / завершено / в среднем дней». `✎` — правка.
  Строки сводных мини-таблиц кликабельны: `miniTable(head, rows, empty, ids)` вешает
  `data-open`, а `openItemById()` закрывает диалог и открывает карточку записи. Так
  работают профиль мастера, профиль пользователя и детализация плиток дашборда. Логин и роль заполняются на будущее.
- **Подразделения**, **Отделы** — общие справочники.

## 4. Ключевые правила, которые легко сломать

1. **Обязательность характеристики зависит от статуса** (`spec.reqStatuses`).
   Пустой массив = обязательна всегда. Так поля «AD и IP» не требуются на складе.
   Проверяется функцией `specReq(sp, status)`.
2. **Группы полей** (`spec.group`) — при применении набора проставляется имя набора;
   в карточке поля идут блоками с заголовком. Кнопка «Отметить группой набора»
   проставляет группу уже существующим характеристикам по совпадению названий.
3. **Уникальность** (`spec.uniq`) считается по **одноимённым** характеристикам во всех
   разделах сразу — поэтому IP не повторится ни у ПК, ни у телефона. MAC сравнивается
   без учёта регистра и разделителей.
4. **Пулы IP**: пул знает своё назначение — раздел и, необязательно, категорию.
   `poolsForSpec()` собирает **все** подходящие: сначала явная привязка `spec.poolId`
   (если есть), затем пулы раздела с этой категорией и пулы раздела без категории.
   Явная привязка не отсекает остальные — иначе при двух подсетях на категорию выбор
   в карточке не появлялся. Поэтому одну и ту же
   характеристику «IP адрес» в разных разделах привязывать вручную не нужно.
   Если подходящих диапазонов несколько, вместо статичного префикса в поле рисуется
   выпадающий список (`data-poolsel`), смена которого переписывает `data-prefix` у input.
   Валидация ищет среди всех подходящих пулов тот, чьему префиксу отвечает адрес.
   Если у характеристики задан `poolId`, в карточке рисуется префикс
   `192.168.203.` + поле только для хоста. Валидация не пропустит чужую подсеть и хост
   вне диапазона. Поле **без** пула не примет адрес, принадлежащий чужому пулу.
5. **Статус «На складе» / «Списано»** прячет и **очищает** ответственного, подразделение
   и отдел; в историю пишется `Снято с сотрудника: ФИО, подразделение, отдел`.
   «В ремонте» — показывает выбор мастера (обязателен), дату и примечание.
   «На складе» у **новой** записи — поле «Кол-во», создаётся N копий (уникальные
   характеристики при этом должны быть пустыми).
6. **Заводские разделы** `equipment / ipphone / supplies / radio` помечаются
   `builtin:true` в `normCfg` по списку `SEED_IDS`. У них нельзя менять название,
   значок и тип, нельзя удалить. Статусы и наполнение менять можно.
7. **Наполнение раздела** (`registry.layout`) — какие вкладки и поля показывать:
   `subs` (подкатегории), `specs`, `presets`, `dash`. Выключенный `subs` скрывает
   вкладку, фильтр, поле в карточке и колонку через класс `body.nosubs` +
   `.col-sub` (класс именно на `body`, иначе не подействует на диалоги).
8. **Статусы раздела** редактируются в диалоге «Настройки раздела». Переименование
   переносится на записи раздела и на `spec.reqStatuses`; удаление статуса переводит
   записи на первый в списке. «На складе», «В ремонте», «Списано» переименовать нельзя —
   Журнал ремонтов ведётся отдельно от записи: `syncRepairLog()` открывает строку при
   переходе в «В ремонте» и закрывает при выходе, поэтому история не теряется после
   возврата в эксплуатацию и переживает удаление записи (в строке лежит снимок inv/типа).
   При возврате из ремонта карточка показывает поля «Дата возврата» и «Что сделали».
   Дни считает `daysBetween()`; у незакрытого ремонта — по сегодняшний день.
   Особые статусы нельзя переименовать —
   на их текст завязана логика карточки и плитки дашборда
   (`ST_USE` / `ST_STOCK` / `ST_REPAIR` / `ST_READY` / `ST_OFF` — все пять в `SPECIAL_ST`).
   `ST_READY` = «Готово к эксплуатации» — промежуточный статус: мастер закончил, технику
   ещё не установили. Он досеивается в статусы существующих разделов в `normCfg`, иначе
   старые конфиги его не получат. Переход в него закрывает ремонт так же, как возврат
   в эксплуатацию, и шлёт уведомление.
9. **Роли**: `isAdmin()` — единственная точка проверки. Пока входа нет, роль лежит в
   `localStorage["it_inv_role"]` и переключается кнопками внизу боковой панели
   (`admin` / `view`). Это **не защита**, а способ спрятать лишнее: любой может
   переключить обратно. Не-админу скрыты `.col-adm` (через `body.noadmin`) и кнопка
   «+ Новый раздел»; `openRegDlg()` и `deleteRegistry()` дополнительно отбивают вызов.
   Мастера назначает только админ: `f_master` и галочка `data-master` у не-админа
   заблокированы, требование выбрать мастера при «В ремонте» действует лишь для него.
10. **Тема**: тумблер `#themeSw` (`.tsw`, солнце/луна) справа от названия «Учёт ИТ-отдела»
   в шапке боковой панели (21.09 — заменил три кнопки «Авто/Светлая/Тёмная» внизу).
   Значения в `localStorage["it_inv_theme"]` те же: `auto` / `light` / `dark`; пока
   пользователь тумблер не трогал, лежит `auto`, и тумблер показывает тему системы
   (`systemDark()`, слушает `prefers-color-scheme`); клик пишет явное `light`/`dark`.
   Крошечный скрипт в `<head>` ставит `data-theme` до отрисовки, чтобы не было вспышки
   светлого на тёмной теме. Подпись под названием — «Единая база».
   **Ловушка стенда:** под `--virtual-time-budget` headless Chrome не проигрывает CSS-переходы
   (`button{transition:.12s}`, `left .18s` у ползунка) — вычисленные `left` и фон после клика
   остаются старыми, хотя класс уже снят. В сценарий/скриншот добавлять
   `<style>*{transition:none !important}</style>`, иначе полчаса ищешь несуществующий баг.
11. **`hidden` сам по себе не скрывает элемент**, если у него есть авторский `display`
   (`.row{display:flex}` перебивала атрибут, и кнопки CSV торчали на всех вкладках).
   В CSS стоит `[hidden]{display:none !important}` — не убирать. В тестах проверять
   видимость по `getBoundingClientRect().width`, а не по свойству `.hidden`.
12. **Выгрузка CSV** разная в трёх местах: `exportCSV()` — записи раздела (только вкладка
   «Записи»); каждая характеристика уходит **отдельной колонкой** (`specColumns()`):
   ОЗУ, диск, БП, ЦПУ, имя ПК, IP — чтобы в Excel их можно было фильтровать и считать.
   Одноимённые характеристики из разных подкатегорий сводятся в одну колонку
   (ключ — название + единица), значение берётся по первому заполненному id.
   Импорт читает те же колонки по названию, так что выгрузку можно править в Excel
   и заливать обратно.

   Рядом с «Экспорт CSV» стоит **«Экспорт Excel»** — тот же набор данных, но настоящий
   `.xlsx`. Книга собирается прямо в браузере: `zipStore()` пишет zip **без сжатия**
   (метод 0 — Excel такие открывает, а кода на дефлейт не нужно), `xlsxSheet()` —
   лист с объединённой шапкой «Характеристики», автофильтром, закреплённой строкой
   и шириной колонок по содержимому. Внешних библиотек нет намеренно: приложение
   должно оставаться одним файлом. Числа пишутся числами, но инвентарные номера и всё
   с ведущим нулём — текстом (`asNumber()`), иначе Excel съедает нули (`0013500`).
   Формат выбирает `expFmt`, обе кнопки зовут один `runExport()`; ragged-отчёты
   (сводка, карта пула) идут через `saveBlock()` в режиме `plain` — без фильтра и
   объединений. Проверять книгу: headless Chrome отдаёт её в base64, дальше `openpyxl`
   (`readxlsx.py`). `exportSupplies()` — склад / журнал приходов / выдачи по активной вкладке,
   `exportDashboard()` — сводный отчёт с общего дашборда (итоги, разделы, статусы,
   подразделения, отделы, материалы), `openIpExport()` — выгрузка IP-адресов с выбором
   колонок: 12 основных плюс любые характеристики по названию (`specValueByName()`
   ищет поле у записи, за которой закреплён адрес). Выбор колонок запоминается в
   `localStorage["it_inv_ipcols"]`. Импорт есть только на «Записях» и на складе.
13. **Фильтры записей** — одна компактная строка без подписей: в каждом селекте первый
   вариант уже говорит, что это («Все категории»), поэтому подписи были лишними.
   Активные фильтры подсвечиваются классом `act` (`markFilters()`), кнопка «Сбросить»
   появляется только когда что-то выбрано, счётчик найденного — в той же строке.
   Блок ужался со 191px до 30px.
14. **Единицы измерения** — не текстовое поле, а список из `cfg.units`, чтобы не плодить
   «шт»/«шт.»/«штук». Последняя опция `＋ добавить свою…` видна только админу и заводит
   новую единицу через prompt. Единицы, введённые до этого вручную, и единицы из
   импортируемых файлов подхватываются в справочник в `normCfg` / `importSupplies`.
   Название материала — `input` с `datalist` из уже заведённых: можно выбрать или
   написать новое, а при выборе известного подставляется его единица.
15. **Таблицы**: `table-layout:fixed` + `<colgroup>` в процентах, строка ровно 44px,
   текст обрезается многоточием, полное значение в `title`.
   **Пиксельные ширины колонок мешать с процентами нельзя** — ломается раскладка
   (проверено: колонка «#» в 42px раздувалась до 200px на узком окне).
   Первая колонка везде — номер строки (3.4%), нумерация пересчитывается после
   фильтрации и сортировки.

## 5. Серверная часть (сделано 15.09.2026)

Папка `server/` — PostgreSQL + Flask:

- `schema.sql` — 22 таблицы: роли, сотрудники ИТ с логинами, сессии, справочники,
  записи учёта, ремонты, расходники, уведомления.
- `app.py` — API и проверка прав; пароли хранятся как `scrypt`-хеш с солью.
- `README.md` — развёртывание на сервере, список прав, автозапуск.
- `.env` — пароль базы и настройки (в переписку и в репозиторий не попадает).

Права выдаются **ролям**, роль назначается сотруднику. Помимо списка прав у роли есть
доступ по разделам: `нет / просмотр / редактирование`. Раздел без доступа **не приходит
клиенту вовсе** — фильтрация в `load_state()`, а не в интерфейсе.

Служебные разделы закрыты не только на кнопках: `NAV_PERM` + `navAllowed()` не пускают
в «Сотрудники ИТ» и «Роли и доступ» без права `staff.manage`, в «Историю удалений» —
без `deletions.view`, а `render()` выкидывает на дашборд, если право отобрали. Раньше
мастер туда заходил, правил форму и получал отказ только при сохранении.

**Учреждения** (16.09) — верхний уровень всего. Таблица `org`, учреждение
сотрудника — поле `staff.org_id` (одно, миграция `007_staff_one_org.sql`), настройки
домена и опроса сети в `org_setting`, право `org.manage`, миграция
`006_organizations.sql`.

**Просмотр по умолчанию** (17.09). Доступ к учреждению не даёт права менять данные:
нужна галочка «Разрешено редактирование» в карточке сотрудника (`staff.can_edit`,
миграция `008_view_only_access.sql`). Проверка стоит и на сервере (`may_write()` в
`/api/cfg`, `/api/items`, `/api/items/delete` → `403 read_only`), и в интерфейсе
(`regLevel()` понижает `edit` до `view`, в боковой панели подпись «только просмотр»).
Тем, кто был заведён раньше, миграция проставила `can_edit = true`: сужать права
молча нельзя, иначе люди утром не смогут работать и не поймут почему.

Роли общие на всю базу, а разделы у каждого учреждения свои — поэтому уровень доступа
ищется и по имени без приставки учреждения (`org_plant2_equipment` → `equipment`).
Без этого роль, настроенная на первом учреждении, молча не работала бы во втором.

**Статус «На списание»** (`ST_TOOFF`, миграция `009_status_to_writeoff.sql`) — техника
ждёт решения комиссии месяцами: в эксплуатации её уже нет, а списанной называть
ещё нельзя. Ставит его любой, кто правит записи; само «Списано» по-прежнему требует
права `item.writeoff`. Владелец при этом сохраняется — комиссия может и отказать.
Миграция досеивает статус перед «Списано» во всех уже заведённых разделах, клиент
делает то же для надёжности в `normCfg()`.

**Право `org.viewall`** — «видеть все учреждения» для начальника отдела: сводка,
сквозные списки и селектор области, но без создания учреждений и без правки.
Раньше это умел только `admin`. На сервере — декоратор `need_view_all`, в интерфейсе
`me.seesAllOrgs` вместо проверки `can("org.manage")`.

Проверка `permtest.py` тогда же нашла две настоящие ошибки:
`/api/cfg` молча отвечал `200` читающему пользователю (ничего не менял, но и не
отказывал), а начальник отдела видел **пустой список разделов** — `load_state()`
считал доступные разделы напрямую по роли, минуя `reg_level()` с его правилами.

Администратор смотрит шире: селектор области на дашборде, в ремонтах, уведомлениях
и журнале удалений («только своё» / конкретное / все сразу). Данные для него приходят
отдельным запросом `/api/cross`, а не в `/api/state`: состояние приложения должно
остаться в рамках одного учреждения, иначе непонятно, в чьи данные пишет сохранение.
На широком дашборде карточки те же, что и в обычном режиме: «Разделы учёта» и
«По подразделениям», только списки общие — одноимённые разделы разных учреждений
складываются по названию. Зато в окне детализации (клик по плитке) первой колонкой
идёт **учреждение**, а сводка сверху считается по учреждениям: иначе строки разных
заводов в одном списке не различить. Карточку записи оттуда не открыть — данных
чужого учреждения в памяти браузера нет. Кнопка «+ Новый раздел учёта» в широком
режиме скрыта: непонятно, в какое учреждение он бы добавился.

Стартовый экран — «Общий дашборд» (`var nav = "dash"`), раньше открывался раздел учёта.
В списке области «Все учреждения» стоит первым пунктом. Всё существовавшее переехало в учреждение
«Основное» (`org_main`), его можно переименовать в карточке.

Разделено: разделы учёта и всё их дерево, записи, пользователи, подразделения,
отделы, наборы, материалы с приходами и выдачами, IP-пулы и резерв, состояние
адресов, ремонты, уведомления, журнал удалений. Общими остались учётные записи
сотрудников ИТ, роли и единицы измерения.

Четыре места, где легко всё сломать:

1. **`sync_table` без `scope` стирает чужое.** Клиент присылает справочники только
   своего учреждения, а функция удаляет всё, чего нет в списке. Каждый вызов теперь
   со своей областью: `org_id` для своих таблиц, `registry_id = any(...)` для
   категорий-подкатегорий-типов, `supply_id = any(...)` для приходов и выдач,
   отдельное условие для характеристик (они висят на подкатегории или типе).
2. **Текущее учреждение приходит из cookie, значит ему нельзя верить.**
   `current_org()` сверяет его со списком доступных и молча возвращает первое
   разрешённое. Проверено подменой: сотрудник с доступом к одному учреждению,
   подсунув чужой id, получает своё, а `/api/org/select` отвечает 403.
3. **`seed()` заводит учреждение раньше разделов.** На чистой установке миграция
   отрабатывает по пустой базе и учреждения не создаёт; если бы `seed()` вставил
   заводские разделы с пустым `org_id`, они не попали бы ни в одну выборку.
4. **Проверять изоляцию надо на явно выбранном учреждении.** Первый прогон
   `orgtest.py` «нашёл» нарушение изоляции, а на деле тест сам брал
   первое попавшееся учреждение: у обоих `sort = 0`, и «Завод-2» встало вперёд
   «Основного» по алфавиту.
5. **Стенд открывается не на дашборде, а на разделе учёта** (`nav = "reg"`).
   Селектор области виден только на дашборде, ремонтах, уведомлениях и удалениях,
   поэтому сценарий проверки должен сначала нажать «Общий дашборд» — иначе у списка
   не окажется вариантов и проверка «не увидит» работающую функцию. Полчаса ушло на
   эту ошибку в тесте, а не в коде.
6. **Ошибки внутри `.then()` не ловит `window.onerror`.** Пока к цепочке
   `loadCross().then(renderAll)` не был приписан `.catch`, сбой отрисовки просто
   исчезал: интерфейс оставался в прежнем виде и ничего не сообщал.

**Опрос сети** (16.09). Сервер обходит адреса и показывает в разделе «IP-адреса»,
кто сейчас в сети и когда отвечал последний раз (`server/netscan.py`, таблица
`ip_status`, миграция `005_ip_status.sql`, право `ip.manage`).

Мерил перед тем, как делать: обход 254 адресов занимает 2 с при 64 потоках и
около 37 КБ трафика — раз в 15 минут это 0,04 КБ/с, то есть нагрузки нет вовсе.
Зато перебор TCP-портов по тем же 254 адресам — 12 с, поэтому он только для тех,
кто не ответил на ping. Это не оптимизация ради оптимизации: **у машин с включённым
брандмауэром Windows ICMP закрыт**, и без стука в 445/3389 половина живых компьютеров
показывалась бы выключенной.

Три места, где легко ошибиться:
`normCfg()` собирает объект из белого списка полей — новый `netStatus` пришлось
добавить туда явно, иначе он молча терялся и колонка показывала прочерки.
Фоновый поток надо поднимать и в `serve.py`, а не только в `__main__` у `app.py`:
на сервере работает waitress, и расписание иначе не запускалось бы.
Настройки перечитываются перед каждым кругом, поэтому включение и смена интервала
не требуют перезапуска.

**Active Directory** (16.09). Справочник пользователей заполняется из домена:
модуль `server/adsync.py` на `ldap3`, экран «Active Directory» в интерфейсе,
права — `users.manage`. Признак отбора задаёт администратор домена в атрибуте
`employeeType` (значение и сам атрибут настраиваются). ФИО собирается как
«Фамилия Имя Инициалы» из `sn` + `givenName` + `initials`; телефон и почта —
новые поля `person.phone` / `person.email` (миграция `004_ldap_users.sql`).
Подразделение берётся из `company`, отдел — из `department`, и оба заводятся сами,
если их ещё нет.

**Учреждение-получатель выбирается явно** (17.09). На экране AD первым полем идёт
«Куда грузить сотрудников»; оно же переключает показанные настройки — они у каждого
учреждения свои. Без этого выбора легко было загрузить людей не туда: человек
смотрит одно учреждение, а грузит в другое. Запросы `/api/ldap*` принимают `orgId`,
`target_org()` сверяет его со списком доступных и на чужое отвечает 403.

Загрузка вынесена в отдельное право **`ad.sync`**: его можно выдать через роль, не
раздавая администраторских прав. Раньше раздел висел на `staff.manage`. Сама кнопка
«Загрузить сотрудников» дополнительно требует разрешения на редактирование.

Поле «Только подразделение AD (OU)» ограничивает поиск веткой дерева: можно указать
полный DN, просто имя подразделения или путь через «/» («Заводы/Завод-1» →
`OU=Завод-1,OU=Заводы,<база>`). Галочка «вместе с вложенными OU» переключает область
поиска между SUBTREE и LEVEL. Раньше тянулось всё дерево домена.

Три решения, которые стоит помнить:
`objectGUID` пишем в `person.ad_guid` — по нему запись находится после переименования
в домене, иначе повторная загрузка заводила бы второго человека. Отключённые учётки
отсеиваются **в коде**, а не фильтром LDAP: битовая проверка
`userAccountControl:1.2.840.113556.1.4.803:=2` есть не в каждом каталоге и её не
понимает мок ldap3. Пароль служебной учётки лежит в `setting` и наружу не уходит —
`public_config()` его вырезает, пустое поле значит «не менять».

Проверять без домена: `adtest.py` поднимает каталог в памяти
(`ldap3` MOCK_SYNC) и гоняет настоящий код разбора и переноса, а изменения в базе
откатывает. В моке нужно класть `objectCategory: "person"` строкой — настоящий AD
разворачивает это в DN схемы сам, поддельный каталог так не умеет.

**Журнал удалений** (16.09, после того как из базы пропала запись и выяснить это было
негде). Удаление записи теперь спрашивает причину: кнопка «Удалить» в окне `dlgDelAsk`
недоступна, пока не написано хотя бы три символа, а сервер без `reason` отвечает
`400 reason_required` — проверка не только в интерфейсе. Перед удалением сервер
складывает в таблицу `deletion` снимок карточки: кто, когда, зачем, раздел, категория,
тип, статус, ответственный, примечание, все характеристики и вся история записи.
Историю иначе не сохранить — `item_history` уходит по cascade. Снимок собирается
на сервере из его же данных, присланному клиентом не верим.

**Накладные** (17.09). Скан перетаскивается в вебку, кладётся в архив и
разбирается на строки; строки пользователь распределяет по разделам сам.
Модуль `server/docscan.py`, таблицы `document`, `sku_hint`, `warehouse`
(миграции 010 и 011), право `docs.scan`.

Главное открытие: **у «требования-накладной» есть текстовый слой PDF**, и данные
оттуда точные — OCR прочитал номенклатуру как 3688287, а слой даёт 4688287.
Поэтому сначала пробуем слой (`pdf_text_layer`), и только для сканов — Tesseract.
Признак скана: в слое меньше 200 значащих символов.

Три ловушки разбора, каждая стоила отдельной правки:

1. **В текстовом слое все строки таблицы склеены в одну.** Читалась только первая
   позиция. Якорь — счёт бухучёта `0\d{5}`, сразу за которым идёт номенклатурный
   номер (`RE_ROW_START`): по нему строка и режется.
2. **Сумма находилась внутри наименования.** «ALCATEL-LUCENT ALE-300 0 5 655 650.00»
   — регулярка ловила деньги начиная с «300», и имя обрывалось на «ALE». Теперь
   сумма засчитывается только отдельным словом.
3. **«Документ № 1172117 от 28.08.2026» разорван на две строки**, да ещё «№»
   в слое выглядит как «No». Ищем по всему тексту связку «номер от дата».

Количество опознаётся по трём знакам после точки (`4.000`) — в этих формах так
печатается только оно, цены идут с двумя. **В скане счёта-фактуры количество
не читается вообще**: цифры не пропечатались, не помогли ни 450 dpi, ни
контраст, ни psm 4/6/11. Это ограничение честно показано — поле остаётся пустым,
пользователь вписывает сам.

Склад-получатель: у счёта-фактуры подписан внизу («Склад - получатель: 0117»),
у требования-накладной стоит последним числом в строке «Получатель»
(«ЦЕНТРАЛЬНЫЙ СКЛАД Завод-1 5004»). Сначала ищем явную подпись, потом «Получателя».

При заведении: наименование из накладной становится **типом** оборудования в
выбранной категории (заводится, если такого нет), номенклатурный номер — в
«Инвентарный номер», количество — столько отдельных записей, статус «На складе»,
склад проставляется из документа. У расходных материалов номенклатура не нужна,
приход идёт одной строкой.

Tesseract ставится на сервер отдельно (`winget install UB-Mannheim.TesseractOCR`),
а **словари едут в пакете** — `server/tessdata/`, 43 МБ, качает `build.py`. В git
их нет. `TESSDATA_PREFIX` подставляется из этой папки, иначе движок видит только
английский.

**Разбор третьего документа и мелкие правки** (17.09, вечер).

`docscan.recognize` к тому моменту стал возвращать **пять** значений (добавился
подбор поворота страницы), а `app.py` распаковывал три — приём файла был сломан.
Признак таких рассинхронов: `ValueError: too many values to unpack`. Починено,
угол теперь уходит в ответ как `angle`.

Оба счёта-фактуры оказались повёрнутыми сканами: подбор поворота выбрал 270° и
90°, и без него текст был бы мусором. Плата — около 12 секунд на документ
(четыре поворота по три секунды). У документов с текстовым слоем разбор
мгновенный.

**В «счёт фактура 2» номер склада не пропечатался** — строка «Склад - получатель:»
есть, а числа за ней нет. Как и с количеством, восстановить нечем. Поэтому на
экране разбора склад теперь **выбирается списком**, а не только показывается:
из накладной подставляется, если прочитался.

Прочее: колонка «Склад» в таблице записей между «Ответственный» и
«Подразделение» (инвентарный номер сужен с 15% до 10% — там максимум 12 цифр);
обновление страницы больше не уводит на «Общий дашборд» — экран запоминается в
`sessionStorage`, а при входе память очищается, чтобы дашборд открывался только
при заходе.

**Офлайн-установка распознавания.** `winget` на сервере без интернета бесполезен,
поэтому установщик Tesseract (48 МБ) кладётся в пакет, ставится командой
`install-ocr.bat` от администратора. Архив вырос до 82 МБ: движок плюс словари.

**Почему распознавание работало у меня и не работало на сервере** (17.09).
`recognize()` ставил путь к словарям через `os.environ.setdefault("TESSDATA_PREFIX", ...)`,
а установщик Tesseract прописывает эту переменную **системно**. На моей машине её
не было — подставлялась наша папка с русским словарём, всё работало. На сервере
переменная уже стояла и указывала на `C:\Program Files\Tesseract-OCR	essdata`,
где лежат только eng и osd. Проверка при этом показывала «готово»: `ocr_status`
пользовался `_tess_env()`, который переменную **перекрывал**. Классическая ловушка —
проверка и работа смотрели в разные места.

Теперь путь присваивается, а не «если не задан», и `ocr_status` отдаёт
`tessdata` с признаком `own`: в разделе «Накладные» видно, какими словарями
пользуется сервер. Проверено в условиях сервера: с системной переменной,
указывающей на папку без русского, распознавание всё равно читает кириллицу.

**Удаление накладных** — через тот же журнал, что и записи учёта: причина
обязательна (короче трёх знаков сервер не примет), в `deletion` пишется номер,
имя файла, склад, число строк и путь в архиве, файл из архива убирается.
Накладную, по которой уже заведены записи, удалить нельзя — иначе у техники
пропадёт основание: сначала удаляют записи.

**Склад-получатель вписывается, а не только выбирается** (17.09). Сначала это был
список уже заведённых складов: номер из накладной подставлялся, но если он не
прочитался — выбрать было нечего, и поле оставалось пустым. Теперь поле с
подсказками (`input` + `datalist`): можно вписать любой номер, незнакомый сервер
заведёт сам, название потом дописывают в справочнике. Подсказка под полем говорит,
что именно произойдёт: «Склада 5004 ещё нет — заведётся при сохранении» или
«Номер склада в документе не прочитался — впишите его сами».

**`start.bat` доставляет недостающие библиотеки** (17.09). Обновление на сервере
сводится к «распаковать поверх и перезапустить», но новая версия может требовать
библиотек, которых нет в старом `.venv`. Так и вышло с распознаванием:
`ModuleNotFoundError: No module named 'pytesseract'`, а интерфейс при этом писал
«распознавание готово» — `ocr_status` проверял только движок и словари. Теперь
проверяются и библиотеки (`missingLibs`), а `start.bat` перед запуском импортирует
их список и при нехватке ставит из `wheels` без интернета. Проверено: снёс
pytesseract/pillow/pypdfium2 из готового окружения — `start.bat` доставил и поднял
сервер.

**Накладная заводится один раз** (17.09). Повторное проведение по тому же
документу удваивало бы технику в учёте. Теперь после заведения статус `applied`,
и `/api/docs/apply` отвечает отказом. Открыть обратно может только администратор
(`/api/docs/reopen`, `need_perm("admin")`) — это нужно, когда OCR не разобрал
строку, сотрудник этого не заметил и провёл документ неполным.

Чтобы при повторном заведении не задвоить уже проведённое, у каждой строки в
`rows_json` ставится `done`. Сверка идёт по паре «номенклатура + наименование».
И ещё: присланные клиентом строки **сливаются** с сохранёнными, а не заменяют их —
иначе строка, которую сотрудник удалил из таблицы, пропала бы навсегда, и дописать
её после открытия было бы неоткуда.

У каждой заведённой записи появляется строка истории: «Заведено по накладной
№ 1172117 от 28.08.2026, склад 5004», автор — тот, кто проводил.

**404 при открытии файла накладной.** `store()` возвращал относительный путь
через `str(Path)`, то есть с обратными косыми: `Северный6 9\файл.pdf`.
`send_from_directory` пропускает такой путь через `safe_join`, а тот на обратных
косых возвращает `None` — Flask отвечает 404. Теперь путь хранится через
`as_posix()`, а при отдаче старые записи приводятся к тому же виду.

**Снова про склейку строк в патчах.** Опечатка `"...text" "...text"` без `+`
рушит **весь** скрипт: `Uncaught SyntaxError: Unexpected string`, интерфейс не
загружается вовсе, а по симптомам похоже на «не работает раздел накладных».
Признак: в шапке осталось `—` вместо имени пользователя, разделы пустые.
В Python такая склейка законна, в JavaScript — нет.

**404 при открытии накладной — две причины сразу** (17.09).

Первая: путь хранился с обратными косыми, `safe_join` такие отвергает (исправлено
`as_posix()` плюс миграция `012_document_paths.sql` для уже сохранённых записей).

Вторая, и настоящая: **мои же проверочные скрипты стирали настройку пользователя.**
Они переключали папку архива на временную через `/api/docs/config`, а в уборке
делали `delete from setting where key='docs'`. После прогона путь исчезал, сервер
брал значение по умолчанию — сетевую шару — и файла там, конечно, не было.
Файл всё это время спокойно лежал на месте. Скрипты теперь запоминают настройку
до подмены и возвращают её в конце; удалять чужие настройки в уборке нельзя.

Отсюда же правило на будущее: **проверочные сценарии не должны трогать
пользовательские настройки** — только свои временные строки, помеченные префиксом.

Голый 404 на этом месте заставлял гадать, поэтому теперь эндпоинт проверяет
наличие файла и отвечает по-человечески: «Файл не найден по пути «…». Проверьте
папку архива: если её меняли после загрузки, файл остался в прежней.»

пароль из существующего `.env` не перезаписывается, иначе слетели бы входы.

**Задача планировщика запускает `pythonw.exe` напрямую.** Сначала она вызывала
посредника `start-hidden.vbs`, который стартовал процесс и тут же завершался: задача
считалась выполненной, процесс жил сам по себе, и `schtasks /end` останавливать было
уже нечего — сервер продолжал отвечать. Проверено: с прямым запуском `/end`

`stop.bat` на всякий случай делает и то, и другое: гасит задачу и снимает процесс,
найденный по порту из `server/.env`.

Кодировка .bat — отдельная история, проверенная тремя прогонами. Сначала писал их
в **cp866**: в консоли верно, а в редакторе сплошные кракозябры — а эти файлы человек
открывает и читает. **UTF-8 с BOM нельзя**: cmd принимает BOM за часть первой команды
(`"﻿@echo" не является внутренней или внешней командой`), `echo off` не срабатывает и
дальше всё сыплется. Итог: **UTF-8 без BOM**, второй строкой `chcp 65001 >nul`, третьей
`set PYTHONIOENCODING=utf-8` — иначе Python при выводе в файл берёт cp1251 и расходится
с консолью. Заодно в питоновских скриптах стоит `sys.stdout.reconfigure(errors="replace")`,
чтобы прямой запуск без `chcp` не падал на символах вроде `─`.

Внутри `echo` нельзя `<`, `>` и **круглые скобки**: первые два cmd считает
перенаправлением («Не удается найти указанный файл»), а `)` закрывает блок `if` раньше
времени — строка `Установите Python 3.14 (64 бита) и поставьте галочку` роняла установку
с `и was unexpected at this time`. В генераторе `mkbat2.py` стоит проверка,
которая ищет такие строки.

Экран «История удалений» (`v-dels`, `renderDels()`, данные — `/api/deletions`) только
показывает: ни строки добавить, ни убрать. Клик по строке открывает `dlgDelInfo` —
карточку удалённой записи целиком. Есть поиск, фильтры по сотруднику и разделу,
выгрузка в CSV и Excel. Удаление раздела пишет в журнал каждую его запись с причиной
«Удалён раздел «…»» — отдельно причину не спрашиваем, она уже в подтверждении.

**База одна — `asset_it`** (настройки в `server/.env`). 16.09 пользователь так и решил:
отдельная тестовая база не нужна, чтобы при переносе на сервер не было путаницы,

### Номера, обязательные поля, узкое окно (18.09.2026)

**Номер записи бывает двух видов** (`inv_problem()` / `next_inv()` в `app.py`,
`invProblem()` / `invKind()` в странице — правила одинаковые, сервер главнее):

- **7 цифр — номенклатурный** (`NOM_LEN`), общий для одинаковых единиц. Если такой
  уже есть в учреждении (по всем разделам), сервер дописывает хвост: `4688287`,
  `4688287/2`, `4688287/3`… Первая единица остаётся с голым номером. Хвост ставит
  только сервер, клиент после сохранения перечитывает состояние (`saveItems` теперь
  тоже делает `loadState()`), иначе в таблице был бы номер без хвоста.
- **10 цифр — инвентарный** (`INV_LEN`), свой у каждой единицы, не трогаем.
- Остальное — опечатка, и слова для каждого промаха свои (заказчик просил именно так):
  меньше 7 — «Неправильный номенклатурный номер», 8 или 9 — «Что вы хотели написать:
  номенклатурный или инвентарный?», больше 10 — «Извините, такого инвентарного номера
  в вашей конторе нет», не цифры — «Номер состоит только из цифр».
- Сначала (утром 18.09) номенклатурный считался восьмизначным — заказчик поправил:
  семь, как и печатается в его требованиях-накладных (4688287, 3662965). Поэтому
  настоящие накладные заводятся без правок номера.
- Проверяется **только новый или изменённый** номер: старые записи с `INV-7` и т. п.
  сохраняются, пока номер не трогают. Ошибка в партии откатывает всю партию
  (`ValueError` внутри транзакции → `bad_inv`, 400).

**Обязательные поля** карточки: категория (если у раздела есть категории),
подкатегория (если она у категории есть и раздел их показывает), тип, склад (кроме
расходных материалов). Проверка в `btnSave` на клиенте; если складов ещё нет, подсказка
ведёт на экран «Склады». В окне накладной обязательны склад-получатель, раздел «Куда» и
категория для оборудования; лишнюю строку убирают крестиком (`js-rowdel`) — раньше её
просто не направляли в раздел. Сервер (`api_docs_apply`) проверяет склад, раздел и
номера **до записи**, чтобы не завести половину накладной.

**Единицы измерения материалов** заводит только администратор: список `units` и так
писал лишь `full`, но кладовщик мог вписать новую единицу материалу через
«переименовать». Теперь клиент это не даёт, а сервер отвечает `bad_value` 400
(«Новую единицу измерения может добавить только администратор»), `save_cfg` для этого
бросает `ValueError`, `api_cfg` её ловит.

**Узкое окно (≤900px)**: панель переезжает наверх и остаётся блоком — выбор учреждения,

Раньше `aside` просто ложился набок: выбор учреждения растягивался, а все кнопки
слипались в один столбец. Подвал с темой и «Выйти» на узком экране виден в одну строку.

### Передача оборудования между складами (18.09.2026)

Таблица `transfer` (миграция 013): кто, когда, откуда/куда (id склада и его подпись
«5004 · Склад ЦС» на момент передачи — склад потом могут переименовать или удалить),
причина, файл накладной. В `item_history` добавлена колонка `transfer_id`: из истории
карточки накладную открывают ссылкой «открыть накладную» (`/api/transfers/<id>/file`).

Как это устроено в карточке: под полем «Склад» галочка **«Передать другому складу»**
(`#f_xfer`, только у уже заведённой единицы оборудования — не у новой и не у
материалов). Она раскрывает блок: склад-получатель (без текущего склада в списке),
примечание к передаче (**обязательно**, отдельное от примечания карточки) и файл
накладной (необязательно). Пока галочка стоит, поле «Склад» заблокировано — его меняет
сама передача.

Сохранение идёт **двумя запросами**: сначала обычный `/api/items` (JSON), затем
`POST /api/transfer` как `multipart/form-data` (`itemId`, `toWh`, `note`, `file`) — JSON
файл не носит. Именно в таком порядке, иначе сохранение карточки затёрло бы новый
склад. Сервер проверяет учреждение, право `edit` на раздел, что склад-получатель есть и
отличается от текущего; кладёт файл через `docscan.store(..., sub="передача")` — в
подпапку `<учреждение>/передача/ГГГГ/ММ`, чтобы не мешаться с приходными; меняет
`item.warehouse_id` и пишет историю «Передано со склада … на склад …: причина
(накладная файл)». Остатки на экране «Склады» считаются по `item.warehouse` — меняются
сами.

Экраны: «Накладные» переименованы в **«Приходные накладные»**, рядом появился экран
**«Накладные по передаче»** (`v-transfers`, `/api/transfers`, поиск, ссылка на файл).
Права отдельного нет: передачу делает тот, кто может править раздел, список видят все
вошедшие в учреждение.

**Между учреждениями (18.09, вечер).** Склад принадлежит учреждению (`warehouse.org_id`,
в карточке склада поле «Учреждение» — только администратор; отдать склад другому
учреждению можно, пока на нём не числится техника текущего, иначе `bad_value`). При
передаче список складов-получателей берётся из `/api/warehouses/all` и группируется по
учреждениям. Если склад чужой, `_move_item_to_org()` переносит запись в одноимённый
раздел того учреждения (`<учреждение>_<раздел>`, иначе по названию, иначе отказ
`no_registry`), заводит там по названиям категорию/подкатегорию/тип, характеристики
переносит по названиям в пределах найденного типа/подкатегории, а чему пары не нашлось —
дописывает в примечание («Характеристики при передаче: …»), чтобы значения не пропали.
`transfer.to_org_id` — накладную видят оба учреждения (`/api/transfers` и файл).

После **любой** передачи запись становится «На складе», ответственный, подразделение,
отдел и мастер снимаются (сотрудник одного учреждения не работает на технике другого;
внутри учреждения технику на новом складе ещё никому не выдали). В историю идут три
строки: «Снято с сотрудника при передаче: …», «Статус: … → На складе» и «Передано со
склада … на склад …. Примечание: …». Слово «Примечание» — по просьбе заказчика, чтобы
причину было видно отдельно.

`item.transferred_at` (миграция 014) — отметка «передано»: ставится передачей, снимается
`save_items`, как только статус уходит с «На складе» (`case` в `on conflict`). В состоянии
это `item.transferred`. В списке (заказчик выбрал из четырёх вариантов): рядом со
статусом второй бейдж «⇢ передано» (`statusCell()`, ячейка `td.st-x` с переносом — иначе
второй бейдж обрезался многоточием), подсказка при наведении — откуда, куда, когда и
примечание из последней передачи (`xferHint()`); над таблицей кнопка-фильтр
«⇢ Переданные: N» (`btnXferOnly`, `xferOnly`), видна только когда переданное есть,
«Сбросить» её тоже снимает.

Клик по строке «Накладных по передаче» открывает `dlgXfer`: все поля, «Карточка
оборудования» (если запись ещё в этом учреждении) и «Посмотреть документ».

Стенд `stub.py` знает `/api/transfers`, но его `fetch` не умеет `FormData`

### Таблица накладной по линейкам бланка (18.09.2026)

Tesseract режет страницу на строки сам, и на бланках М-4 это ломается там, где
наименование занимает две строки: жирный номенклатурный номер стоит между ними по
центру, распознаватель склеивает его с одной строкой, а вторую теряет
(«108000 m ТЕРМОТРАНС…» вместо «4430271 ПРИНТЕР EPSON … ТЕРМОТРАНСФЕРНЫЙ …»).
Ни один `--psm` этого не лечит — проверено на `D:\Projects\document\двухстрочный вид.pdf`.

Поэтому `docscan.table_rows()` режет таблицу сам: горизонтальные линейки → строки,
вертикальные → ячейки (проекции считаются через `Image.resize(BOX)`, без numpy/OpenCV),
шапка находится по словам «Наименование» и «Номенк.», дальше каждая ячейка читается
отдельно: номер — `--psm 7` с белым списком цифр, наименование — `--psm 6` (строки
склеиваются пробелом), количество — `--psm 7`. Ячейки увеличиваются вдвое перед
распознаванием — без этого терялись хвосты слов и путались L/1. `recognize()` теперь
возвращает **шесть** значений, шестое — строки по ячейкам; `app.py` берёт их, а если
таблица по линейкам не нашлась (слабые линии, как у «счёт фактура.pdf») — старый
`parse_rows(text)`. Цена: ~10 с на страницу сверх обычного распознавания.

### Модели, места, «за кем закреплено» (18.09.2026, вечер)

Миграция 015. **Модель** — справочник раздела (`model`, вкладка «Модели» рядом с
«Типы»; добавляет и правит администратор). В карточке поле «Модель» стоит **перед**
«Тип», необязательное. На вкладке — число единиц, клик по модели открывает список с
фильтром `fModel`. Фото (`model.photo bytea`, JPEG до 900 px по большей стороне,
ужимает PIL) грузится отдельным запросом `POST /api/models/<id>/photo`, отдаётся
`GET …/photo`, видно **только** на вкладке «Модели». `hasPhoto` в состоянии, само фото —
нет. При передаче в другое учреждение модель заводится там по названию (без фото).

**Место** (`place`, справочник учреждения, экран «Место» в справочниках) — как
подразделения: `SIMPLE.places`, без колонки «Сотрудников».

**За кем закреплено** — `item.holder`: `person` (ответственный, подразделение, отдел —
как раньше), `place` (`item.place_id`), `item` (`item.parent_id` + `hide_attached`).
В карточке выбор стоит перед «Ответственный сотрудник» и переключает видимые поля
(`syncStatusFields`). К себе и к своим же прикреплённым прикрепить нельзя (в списке их
нет, сервер ещё и `parent = id` обнуляет). Прикреплённое:
- в списке — с показателями корня цепочки (`holderOf()` поднимается диск → компьютер →
  сотрудник, до пяти шагов) и пометкой «(за инв. N)»; с галочкой «Убрать из списка» —
  в списке не показывается (`filtered()`), но в выгрузку попадает (`showHiddenAttached`);
- в карточке того, к чему прикреплено, — блок «Прикреплённое оборудование»;
- в карточке сотрудника — вместе с его техникой, «прикреплено к инв. N» (`itemsOfPerson()`).
За местом — в колонке ответственного «⌖ Серверная». Для «В эксплуатации» обязательны:
за сотрудником — сотрудник/подразделение/отдел, за местом — место, за оборудованием —
родитель. Передача сбрасывает закрепление на «за сотрудником» без ответственного.

Копирайт на дашборде — высотой в две строки текста (`.dash-copy::before` 14 px, без
`padding-top`); нижний отступ `main` — 20 px (был 64).

**Прикреплённое повторяет основное** (`_follow_parent()` в `app.py`): после каждого
сохранения записи сервер копирует прикреплённым статус, дату/примечание статуса, мастера,
склад и отметку передачи — по цепочке до пяти шагов, с историей «Вслед за инв. N: …».
Если прикреплённое сохраняет старый клиент со своим статусом — сервер всё равно
подтянет его к основному. Передача основного увозит и прикреплённое (склад, статус,
в другое учреждение — вместе с разделом/типом/моделью). В карточке прикреплённого
статус, склад, ремонт и характеристики заблокированы с подсказкой «Прикреплено к инв.
N…»; `collect()` шлёт прежние статус/склад/характеристики; чтобы править — сначала
открепить («За сотрудником»). Склад у прикреплённого не спрашивается.

### Вход через Active Directory (18.09.2026, вечер)

`adsync.authenticate(cfg, auth, login, password)`: simple bind **самим пользователем**
(UPN = `логин@суффикс`, суффикс из настроек), после входа — чтение своей записи
(`sAMAccountName`, для DN-логина — base-поиск по DN), отсев отключённых (`userAccountControl`)
и проверка группы (`memberOf`, по DN или по CN). Пароль у нас не хранится — его проверяет
домен, смена пароля в домене ничего не ломает. Проверено на mock-сервере ldap3
(`adauthtest.py`); настоящего домена здесь нет.

Настройки — `setting.adauth` (`enabled, orgId` — чьи настройки домена брать, `suffix,
group, roleId, newOrgId`), экран AD → карточка «Вход через Active Directory», меняет
только администратор (`POST /api/adauth`), `POST /api/adauth/test` — проверка своим
логином и паролем. `staff.auth` (миграция 017): `local` — пароль у нас, `ad` — домен.
`api_login`: сначала локальный пароль (только для `local`), иначе `_ad_login()`: локальные
учётки через домен **не пускаем** (иначе доменный «admin» открыл бы чужой доступ),
`ad`-учётки — проверяем в домене, неизвестный логин — заводим сами с ролью и
учреждением из настроек (`can_edit=false`), ФИО и должность обновляем при каждом входе.
В карточке пользователя ИТ — «Откуда пароль»; при `ad` поле пароля выключено, `pass_hash`
стирается. В списке — чип «AD».

Вход через домен — **дополнение, а не замена**: проект ставится и там, где домена нет,
поэтому учётки с собственным паролем заводятся вручную как раньше, а вход через AD по
умолчанию выключен. Экран входа спрашивает `GET /api/login-info` (без входа) и
показывает подсказку про доменный логин только когда вход через домен включён.

Формы добавления (модели, подразделения, отделы, места) больше не висят постоянно:
кнопка «+ …» (видна только с правом) раскрывает форму, после добавления форма прячется.

**Урок 18.09 (важно):** проверочный скрипт отправил `{"categories": []}` от имени роли с
`ledger.edit` — `sync_table` стёр все категории учреждения (подкатегории и типы потеряли
ссылки). Восстановлено из дампа `before-orgs.dump` от 16.09 (4 категории,

### Первый запуск: администратор задаёт логин и пароль сам (21.09.2026)

Раньше `seed()` заводил `admin` со случайным паролем, печатал его в консоль и клал в
`FIRST_LOGIN_<база>.txt` — в Docker это неудобно (искать в логах), да и файл с паролем
рядом с сервером лишний. Теперь пока в базе **нет ни одного логина** (`has_accounts()`),
`GET /api/login-info` отдаёт `setup: true`, и страница вместо входа показывает форму
`#setupForm` (имя, логин, пароль дважды). `POST /api/setup` заводит `st_admin` с ролью
`role_admin`, `can_edit`, учреждением из `org` и сразу открывает сессию (общий
`_open_session()` с `/api/login`). Условие нарочно строгое — «нет ни одного логина», а не
«нет администратора»: иначе, отключив последнего администратора, любой зашедший на страницу
завёл бы себе нового. Гонка двух одновременных запросов закрыта `lock table staff`,
повторный вызов — `409 already_set_up`. На существующих установках ничего не меняется:
логины есть, экран не показывается.

Забытый пароль — `server/reset_password.py <логин>` с консоли (в Docker —
`docker compose exec app python server/reset_password.py <логин>`): ставит новый пароль,
включает учётку, закрывает её сессии. Старый совет «удалить admin из базы» из УСТАНОВКА.txt
убран — он больше не сработал бы.

Проверено без следов в базе: `setuptest.py` подменяет `app.db()` одним
соединением без commit, удаляет учётки внутри транзакции, гоняет login-info → setup →
state → повторный setup → вход, и делает rollback (логинов до и после — 6). Интерфейс —
`sc_setup.js` на стенде (подмена `fetch` вставляется в `<head>` через маркер `<!--BODY-->`
в `stand.py`, иначе `loadState()` успевает отработать до подмены).

### Загрузка из AD не находила людей, вход через домен не пускал (21.09.2026)

Заказчик настроил всё верно (`employeeType=udf` у людей, служебная учётка, «Проверить
подключение» отвечало «Подключение работает»), но загрузка не приносила никого, а войти
доменным логином не получалось. Причина одна на оба случая — `adsync.search_base()`
склеивал DN вслепую: название подразделения из настроек подставлялось перед базой поиска,
`ГИТ` + `DC=company,DC=local` -> `OU=ГИТ,DC=company,DC=local`. В домене Предприятие это подразделение лежит
глубоко — `OU=ГИТ,OU=Завод-1,OU=Площадка Северная,OU=Severnoye,DC=company,DC=local`, — так что
поиск шёл по несуществующей базе. Хуже того, это не было видно: `Connection` создаётся с
`raise_exceptions=False`, `conn.search()` возвращал `False`, `conn.response` оставался
пустым, и `fetch()` отдавал пустой список как «никого не нашлось». Проверка подключения
делает `bind`, он проходил — отсюда обманчивое «Подключение работает».

Что сделано:

- `resolve_base(conn, cfg)` — название подразделения теперь **ищется в каталоге**
  (`(&(objectClass=organizationalUnit)(ou=ГИТ))` от базы поиска), а не склеивается.
  Путь через «/» («Завод-1/ГИТ») сужает выбор: звенья должны идти по DN снизу вверх по
  порядку, между ними могут быть другие OU. Одноимённых несколько — не угадываем, а
  показываем найденные DN, чтобы администратор уточнил. Полный DN в поле по-прежнему
  берётся как есть. `search_base()` остался для случая «без домена под рукой»: отдаёт
  полный DN или просто базу поиска.
- `fetch()` больше не молчит: `noSuchObject` -> «домен не знает такой базы поиска: …»,
  прочие отказы -> «домен отклонил запрос: …». `sizeLimitExceeded` ошибкой не считается —
  это обычный ответ при `size_limit`.
- `authenticate()` ищет вошедшего **по всему домену** (`baseDn`), а не внутри
  подразделения из настроек загрузки: то подразделение решает, кого переносить в
  справочник, а кому можно входить — решает группа AD в настройках входа. Заодно
  ищем и по `userPrincipalName`, он не всегда совпадает с `sAMAccountName`.
- `/api/ldap/test` отдаёт (через `adsync.probe()`) тот DN, который домен выдал на самом
  деле, — администратор видит, во что развернулось название.
- Страница: подсказка поля стала «ГИТ, или Завод-1/ГИТ, или DN целиком»; сообщение
  «никого не нашлось» называет сам признак («по признаку employeeType = udf») и куда
  смотреть.

Проверено: разбор путей и выбор OU — на подставном каталоге с двумя одноимёнными «ГИТ»
(`t_ou.py`: одно совпадение, два совпадения, уточнение путём, неверный порядок,
несуществующее, полный DN, пусто); `fetch`/`probe`/`authenticate` — на подставном
подключении (`t_fetch.py`: успех, `noSuchObject`, отказ в правах,
`sizeLimitExceeded`, фильтр входа с UPN, отсев по группе). Страница — прогон на стенде:
23 раздела, 21 таблица, горизонтальной прокрутки нет, расхождений `col`/`th`/ячеек нет,
в панели проверки виден настоящий DN.

**Стенд восстановлен.** `stand.py` пропал вместе с временной папкой сессии;
`it-stub.html` пересобирается так: взять блок `<script>` от `window.onerror` до конца
этого тега из старого `it-stub.html` и вставить перед `</head>` свежей страницы
(в файле CRLF — перед склейкой привести к LF). `parse-test.js` тоже пропал: он строится
из страницы — склеить содержимое всех `<script>` без `src`, заменить `.catch(`/`.delete(`
на `.catch_(`/`.delete_(`, сохранить в UTF-16 и прогнать `cscript //Nologo //E:JScript`.
Разбор считается пройденным, если ошибка — уже времени выполнения (например, «объект не
поддерживает свойство или метод "map"»), а не синтаксиса.

### Доступ на сайт ведётся группой AD (21.09.2026)

По решению пользователя вход раздаётся не поимённо, а **группой в домене**: кого
добавили в группу — тот и заходит, заводить учётные записи в приложении не нужно.
Поле «Группа AD, кому открыт вход» было и раньше, но годилось только для простых
случаев, поэтому доведено:

- **Вложенные группы.** Раньше сверялся `memberOf`, а он показывает лишь прямое
  членство: человек в «ГИТ-инженеры», та группа внутри «Asset-IT-Users» — вход
  закрывался. Теперь членство спрашиваем у самого домена правилом
  `1.2.840.113556.1.4.1941` (`in_group_deep()`), домен обходит цепочку сам. Каталог,
  который правила не знает, отвечает ошибкой — тогда возвращаемся к сверке `memberOf`.
- **Название группы в любом виде**: `Asset-IT-Users`, `COMPANY\Asset-IT-Users`,
  `Asset-IT-Users@company.local` или полный DN (`resolve_group()`, `group_name()`).
- **Опечатка больше не «ломает вход всем молча»**: если группы с таким названием в
  домене нет, говорим об этом («группа «…» в домене не найдена»), а не отказываем
  всем как по неверному паролю. Одноимённых несколько — показываем их DN.
- `/api/adauth/test` проверяет группу **отдельно и до пароля** (`check_group()` под
  служебной учёткой) и возвращает её DN и число участников с учётом вложенных.
  На странице после «Проверить вход» видно: «Доступ по группе CN=Asset-IT-Users,… —
  в ней 12 чел.», а при отказе — что человек не состоит именно в ней.
- Пустое поле по-прежнему значит «пускать всех, у кого есть учётка в домене».

**Не путать два разных списка** (в интерфейсе они рядом, и это сбивает):
«Откуда брать сотрудников» с признаком `employeeType` — это справочник людей, за кем
числится техника; «Группа AD» — кто может войти на сайт. Первое про учёт, второе про
доступ, пересекаться они не обязаны.

Проверено на подставном каталоге (`t_group.py`): поиск группы по названию,
в виде `COMPANY\…`, по DN, несуществующая, две одноимённые; членство через вложенную
группу (в `memberOf` её нет), отсутствие членства, каталог без поддержки правила — с
прямым членством и без; вход: пускает по вложенной, отказывает не состоящему, на
опечатке сообщает, пустая группа пускает. Страница — прогон на стенде: 23 раздела,
21 таблица, прокрутки нет, расхождений в таблицах нет, итог проверки входа показывает
группу и число участников.

### Номенклатура, стоимость и документальный склад (21.09.2026)

Заказчик попросил вести цену и номенклатурный номер по всему учёту, а материалы
считать не «по названию», а по партиям. Миграция `019_sku_cost_stock.sql`:
`department.division_id`, `item.sku/cost`, `supply_receipt.sku/cost`,
`supply_issue.sku/cost` и новая таблица `stock_writeoff`.

**Отдел знает подразделение.** В справочнике отделов появилась колонка с выбором —
меняется прямо в строке, отдельного окна ради одного поля нет. В форме добавления
подразделение можно указать сразу.

**У техники — только стоимость.** Поле «Номенклатурный / инвентарный номер»
переименовано в «Инвентарный номер», рядом появилась «Стоимость»: она есть в карточке,
в списке записей (`hide-sm`), в выгрузке и загрузке CSV. Сортировка по ней числовая:
по строке «9» оказалось бы больше «28769000».

Отдельное поле «Номенклатурный номер» у техники сначала было, но заказчик попросил
убрать: **оно дублировало инвентарный номер.** При заведении по накладной
`next_inv(cur, org_id, sku)` и так делает инвентарный номер из номенклатуры — в базе
это выглядело как «инв. 7086302/2, номенкл. 7086302». Колонка `item.sku` в схеме
осталась (миграция 019 уже могла примениться там, где данные успели появиться), но
больше не пишется и не читается; у материалов номенклатура своя и нужна.

**Накладные: «Стоимость» и «Сумма».** Стоимость — цена за единицу из колонки
«Цена в валюте»; в тексте это первая сумма после наименования, её и так находил
`_first_money()` (`money_value()` чистит разряды и запятую). В разборе по ячейкам
добавлена колонка `price` — ищется по слову «цена», именно она, а не «Стоимость
поставки»: та уже итог по строке. Сумма считается сама (`lineSum`) и пересчитывается
прямо при наборе — перерисовывать таблицу на каждую цифру нельзя, поле теряло курсор.
Решение заказчика: «Сумма» = Стоимость × Количество, общий итог документа не берётся.

**Дата берётся из шапки, после «№ Заказ»** (`order_date()`): внизу формы есть
«Документ № … от …», но он читается не на всяком скане, а в шапке дата стоит в обеих
формах. Окно поиска — 120 знаков после слова «Заказ», дальше идут доверенность и её
сроки. Неправильные даты (99.99.9999) пропускаются, а не роняют разбор. Старые правила
остались запасными.

**Материалы считаются по связкам.** Строка остатков — это «материал + номенклатурный
номер + стоимость» (`lots()`, `lotKey()`). Совпало всё — партии складываются в одну
строку; разошлось хоть что-то — отдельная строка со своим остатком. Выдача выбирает
не материал вообще, а конкретную связку, иначе по «Чернила Epson» с двумя
номенклатурами не посчитать, из какой партии ушло. Приход и история поступлений
показывают номенклатуру, стоимость и сумму.

**«Таблица склада» — документальный учёт.** Отдельная вкладка в материалах: приход
общий с фактом, а списания свои (`stock_writeoff`), на «Выдано и установлено» они не
влияют и наоборот. Экран из двух таблиц: сверху **свои остатки** по связкам
(поступило, списано, числится, сумма — `lotDocLeft` = пришло минус списано по
документам), снизу — сами списания; кнопка «Списание» справа в строке поиска, как
«+ Склад» на складах. Первый вариант с карточкой «Документальный учёт» и плитками
показателей заказчик отверг — «в таком виде не нужен». Списание — **акт на несколько материалов** (миграция `020_writeoff_places.sql`
добавила месту строки `division_id`, `department_id`, `warehouse_id`). Первый вариант
списывал по одному материалу за раз, заказчик попросил иначе.

Как устроено. В окне «Списание» сверху выбор связки (материал → его номенклатуры →
цены) и кнопка «+ Добавить в список»; ниже таблица добавленных материалов со
столбцами «Числится», «Списывается», «Сумма». Нажатие на строку открывает **второе
окно** «Куда списать»: строки «Подразделение | Отдел | Склад | Количество» и кнопка
«+ Добавить место» — материал можно разнести по нескольким местам, «Списывается»
показывает сумму по ним. Список отделов сужается по выбранному подразделению — ради
этого и заводилась связь в справочнике отделов; отделы без подразделения показываются
всегда, они ещё не размечены. Разнести больше, чем числится, не даёт ни второе окно,
ни сохранение; материал без единого места сохранить тоже нельзя.

У акта есть **номер** (поле перед примечанием, без него не сохранить) — заказчик
назвал его «основным, что надо знать». В базу акт ложится по строке на материал в
одно место (миграция `021_writeoff_act.sql`: `act` — номер, `act_id` — внутренний
ключ). Группируются строки по `act_id`, а не по номеру: номер человек может повторить
или потом исправить. Строкам, заведённым до миграции, `act_id` проставлен как
`old-<дата>`, иначе список рассыпался бы на строки без номера.

Внизу «Таблицы склада» — **сводка по актам**, а не по материалам: Номер акта · Дата ·
Материалов · Количество · Сумма · Примечание. Нажатие открывает карточку акта с полным
составом (материал, номенклатура, стоимость, подразделение, отдел, склад, количество,

### Области моделей, модель у материала, карточка IP-адреса (22.09.2026)

Миграция `024_model_scope_ip_history.sql`: таблица `model_scope`, `supply.model_id`,
`ip_status.host_name`, таблица `ip_day`.

**Модель знает, где применяется.** Раньше у модели был один раздел. Теперь у неё
несколько областей «раздел + категория + подкатегория» (`model_scope`), категория и
подкатегория необязательны — пустая значит «любая». В окне модели это таблица с
кнопкой «+ Добавить область»; смена раздела сбрасывает категорию, смена категории —
подкатегорию. В карточке записи список моделей сужается по выбранным категории и
подкатегории (`cardModels()`), но только когда есть с чем сравнивать: пока категория
не выбрана, прятать модель рано. У моделей без областей поведение прежнее — годятся
всему своему разделу. Раздел самой модели (`model.registry_id`) держим равным первой
области: по нему модель попадает в выборку состояния.

**У расходного материала тоже есть модель.** Ставится при приходе, хранится у
материала, а не у строки прихода. На «Выдано и установлено» появился отбор «Модель» —
он сужает список материалов; в списке моделей только те, что и правда стоят у
материалов с остатком. На «Таблицу склада» это не распространяется, как и просил
заказчик.

**Материалы: экран разгружен.** Верхний блок с плитками убран. Формы «Приход материала»
и «Выдать / установить» открываются кнопкой и сворачиваются обратно — на этих экранах
чаще смотрят остатки, чем заводят новое.

**«Таблица склада»: нули уходят.** Строка с нулевым документальным остатком больше не
показывается в верхней таблице — приход по ней всё равно виден в «Истории поступлений».

**Карточка IP-адреса вместо перехода в карточку оборудования.** Клик по занятому адресу
открывает окно с именем хоста, состоянием, привязанным оборудованием и **календарём
пингов**: день зелёный, если адрес ответил хотя бы раз за сутки, красный — если
проверяли и не ответил, бледный — если не проверяли. Месяц выбирается списком или
стрелками, за месяц показывается «отвечал / молчал / не проверяли». Кнопка «Карточка
оборудования» осталась в подвале окна.

**Имя хоста опрос узнаёт сам.** Сначала обратная запись DNS (`dns_name`), если PTR нет —
NetBIOS (`netbios_name`): на Windows это `nbtstat -A`, на Linux `nmblookup -A` из
samba-common-bin. В доменной сети PTR заводят не для всех рабочих станций, а имя по
NetBIOS машина отдаёт сама, поэтому один DNS ненадёжен. В образе Docker `nmblookup`
не стоит — там работает только DNS; если понадобится, пакет добавляется в Dockerfile.
Имя показывается в карточке адреса и в подсказке на сетке, без открытия карточки.

Разбор вывода (`parse_netbios`) понимает обе программы: у `nbtstat` это
«PC-IVANOV <00> UNIQUE Registered», у `nmblookup` — «PLANT1-PC01 <00> - B <ACTIVE>»,
слова UNIQUE там нет, зато групповые записи помечены GROUP — их отсеиваем, как и
`MSBROWSE`. Имя ловится только внутри одной строки (`[^<
]`): без этого ленивый
шаблон перепрыгивал через перевод строки и утаскивал в имя шапку «Looking up status of…».

Как считается история: `netscan.run()` на каждый обход пишет строку в `ip_day`
(`alive = ip_day.alive or excluded.alive`, плюс счётчики `seen`/`checks`) и удаляет
всё старше `HISTORY_DAYS = 183` — полгода, как просили. Имя хоста берётся обратным
разрешением и только у ответивших: у молчащего адреса запрос упёрся бы в таймаут
резолвера и растянул обход. Готовое имя не затирается пустым.
`GET /api/ip/history?ip=…` отдаёт сразу все полгода — это максимум 183 строки, меньше
килобайта, зато перелистывание месяцев идёт без похода на сервер.

Проверено. Стенд при 1440, 1024 и 820 px: плиток нет, формы прихода и выдачи
сворачиваются, отбор по модели сузил материалы с 5 до 3, у модели 2 области (добавление
и удаление работают), в календаре 14 зелёных и 8 красных дней, 7 месяцев в списке, имя
хоста PC-IVANOV показано, кнопка карточки оборудования на месте, нулевых строк в
документальных остатках нет. База — круговой прогон в транзакции с откатом: обе области
модели и модель у материала доезжают и возвращаются, следов не осталось.

### Количество в списании, «Без модели», номер из «№ Заказ» (22.09.2026)

**Количество в местах списания больше не подставляется молча.** `readWoDest()`
возвращал `Math.max(1, parseInt(...) || 1)` — добавил строку с подразделением и
складом, забыл количество, и списалась единица, о которой никто не просил. Теперь
значение читается как есть, а `woDestProblem()` проверяет каждую строку: пусто —
«не указано количество», дробное — «количество целое число», ноль или минус —
«должно быть больше нуля». Проверка идёт и в окне мест по «Готово», и при сохранении
всего акта. Минус вообще не набирается: знак снимается прямо при вводе, у поля
`min="1"`. Новая строка места заводится с пустым количеством, а не с единицей.

**Галочка «Без модели»** — в приходе материала и в отборе на «Выдано и установлено».
Пустой пункт в списке уже был, но заказчик просил показать, что поле необязательное,
явно. Галочка запирает список и очищает выбор.

**Номер документа берётся из «№ Заказ»**, а не из «№ документ» (`order_number()`).
Окно поиска — 80 знаков после слова «Заказ», обрезается по «Основание», «Получатель»,
«Отправитель», «ИНН» и «Доверенность»: за ними идут чужие числа. Даты из окна
вырезаются, чтобы «28.08.26» не сошло за номер. Берём 5–9 цифр: меньше нельзя, иначе
в форме М-11 вместо номера подхватывается склад «0117» или графа «19».

Если номер заказа не прочитался, остаётся прежнее правило — «Документ № … от …»
снизу. Так и вышло на реальной М-11 (`требования накладная.pdf`): в её шапке
«No документ j No Заказ 28.08.26 19 |0117| 60» номер заказа не распознался, и номер
взялся снизу — 1172117. Если в этой форме заказ всё-таки есть, нужен скан, где он
читается.

Проверено. Разбор шапки на придуманных строках: «Заказ 44583 28.08.26» -> 44583;
без заказа -> прежний 81527; числа за «Основанием» не берутся -> 1172117. Стенд при
1440, 1024 и 820 px: пустое количество и ноль отклоняются с сообщением, минус не
набирается, галочки «Без модели» запирают списки, прогон чистый.

### Что за устройство на адресе (22.09.2026)

В сети не только компьютеры — IP-телефоны, камеры, видеорегистраторы, коммутаторы,
радиомосты, принтеры. Заказчик попросил собирать по каждому адресу максимум.
Модуль `server/netinfo.py` и миграция `025_ip_details.sql`
(`ip_status`: `mac`, `vendor`, `ports`, `banner`, `kind`, `probed_at`).

Что собирается и откуда:

- **MAC** — из таблицы ARP самой машины (`arp -a`, на Linux `ip neigh`). Она уже
  заполнена только что прошедшим пингом. Через маршрутизатор ARP не виден, так что
  MAC будет только у адресов своей сети; своего адреса в таблице тоже нет.
- **Производитель** — по первым трём байтам MAC. Справочник IEEE лежит в
  `server/oui.txt`: 40 101 запись, 778 КБ, собран скриптом `make_oui.py`
  из `standards-oui.ieee.org/oui/oui.csv` с подрезкой названий («Hangzhou Hikvision
  Digital Technology Co.,Ltd.» -> «Hangzhou Hikvision»). Локально назначенные адреса
  (второй бит первого байта) пропускаются — производителя по ним не узнать.
- **Порты** — 18 характерных: 21, 22, 23, 80, 135, 139, 443, 445, 515, 554, 2000,
  3389, 5060, 8000, 8080, 9100, 34567, 37777. Список подобран, чтобы различать
  классы техники, а не переписать всё открытое: каждый лишний порт — ещё одно
  соединение на каждый адрес.
- **Баннер** — `Server` и `<title>` веб-интерфейса (80, 8080, 8000, 443, 8443).
  Самая говорящая строчка из доступных без пароля: у камер в титуле прямо написан
  производитель, у коммутаторов — модель.
- **Тип** (`guess_kind`) — догадка по совокупности вендора, портов, баннера и имени:
  принтер, камера, видеорегистратор, IP-телефон, компьютер, радиомост, коммутатор,
  «устройство с веб-интерфейсом». В карточке она стоит рядом с портами и баннером,
  чтобы человек видел, на чём догадка основана.

**Разбор не на каждый обход.** Он тяжелее пинга — полтора десятка соединений плюс
запрос к веб-интерфейсу, на один адрес уходит до десяти секунд. Поэтому `deep_pass()`
берёт только тех, о ком ничего не знаем или знаем сутками старше (`DEEP_EVERY_H = 24`),
и не больше `DEEP_PER_RUN = 60` за обход, в десять потоков. Расписание обхода от этого
не разъезжается. Пустым ничего не затирается: MAC виден не всегда, веб-интерфейс мог
не ответить в этот раз.

**В карточке адреса — только нужное.** Заказчик убрал «Открытые порты», «Веб-интерфейс»,
«Сейчас», «Разобран» и «Резерв». Осталось: имя хоста, что за устройство, производитель,
MAC-адрес, последний ответ, оборудование и ответственный. Порты и баннер по-прежнему
собираются и лежат в базе — на них держится определение типа, — просто в карточке их
не показываем.

**Чем подписывается адрес.** По просьбе заказчика порядок такой: имя хоста, если его
нет — производитель по MAC, если нет и его — тип устройства (`netDevice()`). У камер и
коммутаторов имени обычно нет вовсе, зато производитель известен почти всегда.

Учёт при этом главнее догадки: если адрес заведён в учёте, в сетке стоит ответственный
или инвентарный номер, а данные опроса видны в подсказке и в карточке адреса. Подпись
из опроса подставляется тем адресам, которых в учёте нет, — раньше они были просто
пустыми. В выборе подписи для выгружаемой карты добавились «Имя хоста» и «Что за
устройство».

**Тип — только когда уверенно.** Раньше `guess_kind()` на любой открытый веб-интерфейс
отвечал «Устройство с веб-интерфейсом». Так нельзя: веб-морда есть и у камеры, и у
коммутатора, и у ИБП. Теперь в таком случае возвращается пусто, и непустой тип значит,
что опрос в нём уверен.

SNMP не трогали: он дал бы больше всего по коммутаторам, но требует community-строки
и своей библиотеки, а проверить его здесь не на чем.

Проверено вживую на этой машине: собственный адрес -> порты `135,139,445,8000`, баннер
«Учёт ИТ-отдела · Werkzeug/3.1.8», тип «Компьютер»; шлюз 192.168.100.1 -> MAC найден,
баннер «4G UFI». Справочник: Ubiquiti, Hewlett Packard, Hangzhou Hikvision, Hangzhou
H3C по тестовым MAC; случайный локальный адрес даёт пусто. Сквозной прогон через
`deep_pass` на рабочей базе в транзакции с откатом: строка заполнилась, повторный
прогон в те же сутки вернул 0, следов не осталось. Стенд: в карточке адреса видны тип,
производитель, MAC, порты и баннер.

### Характеристика, которой может быть несколько (22.09.2026)

Второй диск, третья планка памяти. Миграция `026_spec_slots.sql`: `spec.multi` и
`item.spec_slots`.

**Как хранится.** Значения остались в `item.specs`, но у второй строки и дальше ключ
с номером: `s1` — первая, `s1#2` — вторая, `s1#3` — третья. Так всё, что читает
`specs[id]` (экспорт, поиск, проверка уникальности, импорт CSV), продолжает видеть
основное значение и ничего не ломается. Служебное — откуда строка взялась и когда её
сняли — лежит отдельно в `item.spec_slots` тем же ключом:
`{"s1#2": {"src": "item:itm…", "off": "2026-09-12"}}`.

**Где разрешено.** Только у характеристик с галочкой «Может быть несколько» — она
есть и в форме создания, и в таблице характеристик. У IP-адреса и имени ПК её не
ставят, и проверка на повторы по ним продолжает работать как прежде.

**В карточке.** Под основной строкой идут добавленные — «HDD 2», «HDD 3» — и кнопка
«+ ещё HDD». У каждой добавленной: «Снять», «Вернуть» и ✕ «Убрать строку». По решению
заказчика снятая строка **остаётся видимой** с пометкой «снято ДД.ММ.ГГГГ» и своим
значением: место держится за прежней деталью, пока её не заменят, и номера не
сдвигаются. Обязательной бывает только первая строка.

**От запчасти.** Заказчик выбрал «и вручную, и от запчасти», поэтому строку можно
завести двумя путями:

- материал: в «Выдать / установить» при цели «На оборудование» появился выбор
  «Занимает характеристику» — подставляются свободные строки выбранной техники
  («HDD 3»), и при списании материал вписывается туда, а в историю идёт
  «Установлено: HDD 3 — Чернила…»;
- оборудование: в карточке детали при «За оборудованием» появился такой же выбор по
  характеристикам основного. Значение берётся из самой детали: одноимённая
  характеристика, иначе модель, иначе тип, иначе инвентарный номер. Основное
  оборудование сохраняется тем же запросом (`saveItems([o].concat(extra))`) — иначе
  правка потерялась бы.

Строка, заполненная запчастью, помечена значком ⚙.

**Колонка «Правила» под четыре галочки.** Четвёртая («несколько») была на месте, но
обрезалась: у `td.rules` стоял `white-space:nowrap;overflow:hidden`, а колонка была
23% — на 1440 px содержимое требовало 337 px при ширине ячейки 264. Теперь галочки
переносятся на вторую строку (`white-space:normal`, высота ячейки по содержимому), а
сама колонка расширена до 29% в характеристиках и до 33% в наборах. Замер после
починки: при 1920, 1440, 1280 и 1024 px все четыре видны целиком, строка растёт с 44
до 54 и 74 px.

**Наборы тоже умеют «несколько».** Галочка добавлена в форму «Добавить характеристику
в набор» и в список набора; при применении набора признак переносится на заведённые
характеристики (`multi: !!t.multi`). Заодно исправлено: галочка в форме новой
характеристики не сбрасывалась после добавления, и следующая молча получала «несколько».

Проверено. Стенд при 1440, 1024 и 820 px: у записи видны «HDD, Gb» и «HDD 2, Gb»,
кнопка «+ ещё HDD» добавляет «HDD 3», «Снять» ставит пометку и не стирает значение,
«Вернуть» её убирает, ✕ убирает строку; у IP-адреса кнопки «ещё» нет; в выдаче
материала предлагается занять «HDD 3». База — круговой прогон в транзакции с откатом:
галочка «несколько» сохранилась, оба значения (1000 и 2000) вернулись, пометки
`src` и `off` тоже; следов не осталось.

### Характеристику подкатегории можно отключить у отдельного типа (22.09.2026)

Стандартные характеристики подкатегории действуют у всех её типов — это удобно, пока
какому-то типу что-то из них не нужно. Раньше унаследованную строку на уровне типа
можно было только смотреть («в подкат.»), теперь у неё есть кнопка **«Убрать»**, а у
убранной — **«Вернуть»**. Миграция `027_type_hidden_specs.sql`: `item_type.hidden_specs`
— список отключённых характеристик этого типа.

Сама характеристика при этом остаётся у подкатегории и у остальных типов: отключение
живёт у типа, а не у характеристики. Отключённая строка не исчезает из списка, а
помечается «не используется» — иначе её нельзя было бы вернуть. `specsOf()` такие
отсеивает, поэтому в карточке записи их нет и обязательными они не считаются.

Проверено. Стенд при 1440, 1024 и 820 px: у унаследованной строки есть «Убрать», после
нажатия появляется пометка «не используется» и кнопка «Вернуть», в карточке записи
характеристика пропадает, «Вернуть» возвращает её. База — круговой прогон в транзакции
с откатом: `hiddenSpecs` сохранился и вернулся, следов не осталось.

### Готовый набор принадлежит своему разделу (22.09.2026)

Наборы лежали общим списком, поэтому набор «Компьютер», заведённый в «ПК и сетевом
оборудовании», торчал и в IP-телефонах, и в рациях, и в расходных материалах. Теперь у
набора есть раздел: миграция `028_preset_registry.sql` добавляет `preset.registry_id`,
новый набор получает текущий раздел, а `regPresets()` отдаёт только свои. Отбор
действует и в списке наборов, и в выпадашке «применить набор» — применить чужой набор
к типу больше нельзя.

Наборы, заведённые до этого, раздела не имеют и остаются общими: они видны везде и
помечены «общий», а кнопка **«Закрепить за этим разделом»** проставляет им раздел.
Молча раскидывать их по разделам нельзя — неизвестно, для чего они заводились.

**Подпись «всегда» убрана.** Под галочкой «обяз.» висел чип «всегда», который ничего не
добавлял: обязательность и так видна по самой галочке. `reqChip()` теперь возвращает
подпись только когда обязательность сужена статусами («при: в работе, на складе») —
вот это по галочке не увидеть.

Проверено. Стенд при 1440, 1024 и 820 px: набор, созданный в «ПК и сетевом
оборудовании», в рациях не появляется, чипа «всегда» в правилах нет, остальной прогон
без изменений. База — круговой прогон в транзакции с откатом: раздел у набора
сохранился и вернулся, следов не осталось.

### Передача в другое учреждение: прикреплённая техника остаётся (22.09.2026)

Раньше при передаче системного блока в другое учреждение за ним уезжало и всё
прикреплённое: диски, память, монитор — их записи переносились в разделы получателя.
Так нельзя: это отдельные единицы на балансе нашего учреждения, и списать их с учёта
передачей одного системного блока невозможно.

Теперь при передаче **в другое учреждение** прикреплённая техника открепляется и
остаётся у себя: тот же раздел, тот же склад, статус «На складе», ответственный,
подразделение и отдел сняты, пометка «скрыто в списке» убрана — запись снова видна в
общем списке. Причина в том, что ответственного прикреплённая запись не хранит вовсе:
он берётся от основного при показе. Основное уехало — брать неоткуда, поэтому
самостоятельной записи полагается «На складе».

Установленные материалы, наоборот, остаются с техникой: отдельной записи у них нет,
со склада они уже списаны, и выдачи считаются по учреждению материала — то есть в
книгах отправителя.

Передача **внутри учреждения** не изменилась: там прикреплённое по-прежнему едет за
основным (`_follow_parent`) — склады свои, техника остаётся на том же балансе.

Что добавилось: `_detach_children()` в `server/app.py`, строка в истории у каждой
откреплённой записи («Откреплено от инв. N — основное передано на склад X. Осталось
на складе Y, статус: … → На складе») и у основного («Откреплено при передаче: …»).
`/api/transfer` отдаёт список откреплённого, по нему страница пишет уведомления
(тип `detach`, значок «⇥») и показывает счёт в подсказке после передачи.

Проверено. База — прогон в транзакции с откатом: заведены основное со складом и
ответственным и прикреплённое к нему, скрытое из списка; после передачи в другое
учреждение основное сменило раздел и склад, прикреплённое осталось в своём разделе и
на своём складе, откреплено, снова видно, «На складе», без ответственного, обе записи
истории на месте; после отката tmp-строк 0. Стенд при 1440 и 1024 px — без изменений.

### Тип устройства убран, окно адреса больше не прыгает (22.09.2026)

**Тип устройства убран совсем.** Догадка по производителю, открытым портам и
заголовку веб-интерфейса слишком часто врала, а держать в карточке поле, которому
нельзя верить, хуже, чем не иметь его вовсе. Убрано: `guess_kind()` со списками
вендоров в `netinfo.py`, строка «Что за устройство» в карточке адреса, подпись
«Что за устройство» в выборе подписи на карте адресов, функция `netDevice()` и тип
в подсказке ячейки. Подпись адреса теперь такая: имя хоста, без него —
производитель по MAC, без обоих — точка.

Вместе с типом ушёл и опрос портов: показывать его было негде (порты и
веб-интерфейс из карточки убрали ещё раньше), а каждый обход он затягивал полутора
десятками соединений на адрес и со стороны выглядел сканированием сети. Из
`netinfo.py` убраны `PORTS`, `port_open`, `scan_ports`, `http_banner` — осталось
90 строк: таблица ARP и справочник OUI. `deep_pass()` стал лёгким (только чтение
ARP и поиск по справочнику), поэтому пул потоков в нём заменён обычным циклом, а
аргумент `names` убран — имя хоста пишет обычный пинг-проход, не разбор.

Колонки `kind`, `ports`, `banner` в `ip_status` остались, но больше не пишутся и не
читаются: миграцией их не сносил, чтобы ничего не терять — если тип когда-нибудь
понадобится, места под него не надо заводить заново.

**Окно адреса зафиксировано.** В месяце то пять недель, то шесть, и календарь менял
высоту при каждом перелистывании — браузер центрирует `dialog`, поэтому окно
дёргалось вверх-вниз. Теперь сетка всегда шесть недель (недостающие клетки —
пустые), а строки заданы явно: `grid-template-rows:18px repeat(6,38px)`. Замер на
стенде: пять переключений месяца подряд — высота 632 px и верхняя граница на месте.

**Счёт «отвечал: N, молчал: M» убран** — блок `#ipMonthStat` после выбора месяца.
Цветная подпись под календарём (отвечал / не отвечал / не проверяли) оставлена: она
объясняет, что значат цвета клеток.

Проверено. Стенд при 1440, 1024 и 820 px: «Что за устройство» и счёта в окне нет,
тип устройства не попадает в подписи адресов даже когда он лежит в данных, высота
окна не меняется, календарь и выбор месяцев работают. Обход сети — прогон на
настоящем адресе в транзакции с откатом: разбор отмечается, порты, баннер и тип не
пишутся, производитель по MAC определяется («bc:ad:28» → Hangzhou Hikvision),
повторный прогон в те же сутки ничего не делает, после отката строк 0.

### Экран «Склады» снова показывает склады (23.09.2026)

Склады были в выпадающих списках карточки, а на своём экране таблица оставалась
пустой. Причина — **два разных куска кода делили имена**. Когда появилась
«Таблица склада» в расходных материалах, её функцию тоже назвали `renderWh`, а
её таблице дали `id="whBody"` и `id="whEmpty"` — ровно как у экрана складов.

Дальше всё ломается тихо: объявление функции ниже по файлу затирает верхнее, и
`renderWh()` из общего рендера рисовал таблицу расходников, а не складов. Да и
рисовать было некуда — `getElementById("whBody")` отдаёт **первый** элемент в
документе, то есть опять расходники. Ошибки в консоли при этом нет.

Разведено по именам: у экрана складов теперь `renderWhs()`, `whsBody`, `whsEmpty`
(обработчик клика и поиск `qWh` переведены туда же), в общем рендере вызывается
`renderWhs()`. У расходников всё осталось как было: `renderWh()`, `whBody`,
`whEmpty`, `qWh2`.

Проверено на стенде (три склада в данных, у первого числится одна позиция):
экран виден, строк 3, плашка «Склады пока не заведены» скрыта, номер первого
склада 5004, «Позиций» = 1, поиск «рудник» оставляет одну строку; таблица списаний
расходников на месте; горизонтальной прокрутки нет, расхождений `col`/`th`/ячеек
в 39 таблицах нет.

### Характеристики переезжают вместе с техникой (23.09.2026)

Раньше при передаче в другое учреждение характеристики искались у получателя по
названию, а чему пары не нашлось — сваливалось строкой в примечание
(«Характеристики при передаче: RAM=32; SSD=512»). Значение формально не пропадало,
но переставало быть характеристикой: по нему не искать, не выгрузить, не поправить.

Теперь переезжает всё. Для каждой характеристики:

- **у типа-получателя или его подкатегории есть одноимённая** — берём её, ничего не
  заводим. Заказчик про этот случай сказал прямо: «если такое оборудование с такими
  характеристиками уже есть, то ничего не изменится»;
- **нет** — заводим такую же **у самого типа**. Это его собственная характеристика:
  подкатегория и остальные типы получателя не трогаются, а дальше её правят как
  любую другую — переименовать, поменять вид, убрать.

Что переносится в новую характеристику: название, вид, единица измерения, варианты
списка, группа в карточке, «уникальна», «разрешено „нет значения“», «может быть
несколько». Две вещи сознательно не переносятся: **обязательность** (`req`,
`req_statuses`) — иначе прежние записи этого типа у получателя вдруг перестали бы
сохраняться без нового поля; и **привязка к пулу адресов** (`pool_id`) — пулы у
каждого учреждения свои.

### Вход через домен: искали человека не по всему домену (23.09.2026)

Жалоба: «группу проверил — видит 7 чел., но некоторые всё равно не заходят».

**Причина.** `authenticate()` искал запись вошедшего от `baseDn` — того самого
«Корня поиска» из настроек **загрузки сотрудников**. Если там указано
подразделение (`OU=Завод-1,OU=Площадка Северная,OU=Severnoye,DC=company,DC=local`), а человек
лежит в соседнем (`OU=Завод-2,…`), поиск его не находил — и вход закрывался, хотя в
группе доступа он состоял. Со стороны это выглядело как «домен не принял пароль»:
`authenticate()` в обоих случаях возвращает `None`. Комментарий в коде при этом
уверял, что ищем «по всему домену, а не внутри подразделения из настроек загрузки»
— намерение было верное, а строка ниже брала `baseDn`.

Та же ошибка была в счётчике группы: `check_group()` считал участников тоже от
`baseDn`. Отсюда «в ней 7 чел.» при большем числе на самом деле — остальные просто
лежали вне корня.

**Починено.** И вход, и счёт группы идут от корня домена: `domain_root()` оставляет
от `baseDn` только части `DC=` (`OU=…,DC=company,DC=local` → `DC=company,DC=local`). Настройки
загрузки по-прежнему решают, **кого переносить в справочник сотрудников**; кому
**входить** — решает группа AD, как заказчик и просил 21.09.

Значит, ответ на вопрос «влияет ли верхний блок загрузки сотрудников на вход»:
раньше влиял, и вредно. Теперь от него остаются только адрес сервера, порт, SSL и
служебная учётка — то, без чего к домену не подключиться. Поля «Откуда брать
сотрудников» (OU) и признак `employeeType` на вход не влияли и не влияют.

**Новое: «Почему не заходит».** В карточке «Вход через Active Directory» рядом с
«Проверить вход» появилось поле для логина и кнопка. Пароль проверяемого **не
нужен** — сервер смотрит служебной учёткой и отвечает по шагам:

- есть ли такой в домене (ищем и по `sAMAccountName`, и по UPN, от корня домена);
- где именно лежит (DN) и попадает ли под корень загрузки — теперь это только
  про справочник сотрудников, не про вход;
- включена ли учётная запись в домене;
- состоит ли в группе доступа с учётом вложенных, сколько человек в группе видно
  из корня загрузки и сколько из всего домена (расхождение сразу показывает, что
  корень узкий);
- не заведена ли у нас учётка с тем же логином, но с нашим паролем — такие через
  домен не пускаются (`_ad_login`), и это вторая частая причина;
- не отключён ли человек уже у нас.

Маршрут `POST /api/adauth/probe`, только администратору. Причины возвращаются
списком `why`, на странице печатаются под кнопкой.

Проверено на подставном каталоге (`t_probe.py`, `t_auth.py`): при узком
корне человек из соседнего подразделения раньше не находился, теперь вход ищет от
`DC=company,DC=local` и пускает его; неверный пароль по-прежнему не пускает; отключённая
учётка не пускает; не состоящего в группе не пускает; несуществующий логин —
«в домене не найден». Счёт участников группы: из узкого корня 2, из домена 3 —
разница видна в ответе проверки. Маршрут через сервер: без входа 401, пустой логин
400 «Укажите доменный логин», логин при ненастроенном домене — 400 с текстом ошибки
подключения. Стенд: поле и кнопка на месте, ответ печатается целиком,
горизонтальной прокрутки нет.

**Чего проверить не могу.** Настоящего домена на машине разработки нет — всё выше
проверено на подставном каталоге. На рабочем сервере стоит прогнать «Почему не
заходит» по тем, кто не входил, и посмотреть, что скажет.

### Пароль при проверке входа, метка прикрепления, сортировка колонок (23.09.2026)

**Пароль больше не виден.** «Проверить вход» спрашивал логин и пароль через
`prompt()`, а он показывает набранное открытым текстом — пароль читал любой, кто
стоит рядом. Теперь обычное окно `dlgAaTest` с полем `type="password"`; после
нажатия «Проверить» поле сразу очищается. Остальные `prompt()` в странице спрашивают
названия и примечания — пароля среди них нет, проверил.

**Прикреплённое видно в списке.** Галочка «убрать из списка» у прикреплённой техники
делала запись невидимой в общем списке совсем: найти, что к чему прикреплено, можно
было только перебором карточек. Теперь:

- в строке стоит метка **⛓** с подсказкой «В составе инв. 0013500» и, если запись
  скрыта, «, скрыто из общего списка»;
- в фильтрах появился выбор **«прикрепление»**: «любое» (как раньше — скрытые не
  показываются), «Показывать и скрытые», «Только прикреплённые», «Только скрытые из
  списка», «Только самостоятельные». Считается в «Сбросить» наравне с остальными;
- общий поиск теперь ищет и по инвентарному номеру основного: набрал номер
  системного блока — в списке он сам и всё, что к нему прикреплено.

**Сортировка по любой колонке.** У таблицы записей она была и раньше — там сортируют
по полям, а не по тексту ячейки (иначе стоимость «9» оказалась бы больше
«28 769 000»), её не трогали. Всем остальным таблицам добавлена сортировка по клику
на заголовок: первый клик — по возрастанию (↑), второй — по убыванию (↓). Числа и
даты `дд.мм.гггг` распознаются и сравниваются как числа и даты, а не как строки;
колонка «#» перенумеровывается, потому что это номер строки, а не данные.

Сделано одним обработчиком на всю страницу, без правки двух десятков функций
отрисовки: клик ловится делегированием, выбранный порядок хранится в `tblSort` по
ключу таблицы, а возвращается после перерисовки через `MutationObserver` на теле
таблицы.

**Грабли с наблюдателем.** Первая версия вешала браузер намертво: `applyTblSort`
переставляет строки → наблюдатель видит изменение → сортирует снова, и так по кругу.

стоят как надо, DOM не трогаем вовсе, и цепочка обрывается на втором шаге.

### Модели у расходников и печать «Номенк.» (23.09.2026)

**Почему модели не подтягивались в расходники.** `supplyModels()` отбирал модели по
разделу расходников (`modelFits(m, curReg, ...)`), а ни одна модель к нему не

бывает**. Материал ставится в технику, и модель у него та же, что у железа
(«Seagate 1 ТБ» — и запчасть на складе, и диск в компьютере); если завести модель
«для расходников», её потом некуда будет применить — ни в ПК, ни в рациях.

Поэтому сделано наоборот: разделы расходников убраны и из формы новой модели, и из
таблицы областей применения (`assetRegs()` вернулась), а **`supplyModels()` отдаёт
все модели техники**. В списке на приходе материала они разложены по разделам через
`optgroup` — видно, к какой технике модель относится.

**Печать «Номенк.»** — кнопка **в карточке оборудования**, в подвале рядом с
«Удалить». Печатает наклейку на эту одну запись; у новой, ещё не сохранённой,
кнопка скрыта — печатать нечего. Сначала кнопка стояла над списком и печатала всё
отфильтрованное, но заказчик поправил: нужна карточка.

Наклейка повторяет `D:\Projects\document\номенк.docx`: инвентарный номер жирным с
отступом, под ним название типа мелким шрифтом, внизу склад («код + название»)
жирным. Шаблон — `server/nom_template.docx`, сделан из файла заказчика заменой
текста на метки `{{ИНВ}}`, `{{ТИП}}`, `{{СКЛАД}}`; блок из трёх абзацев размножается
по числу записей (маршрут принимает список, просто из карточки он всегда из одной).

**Ширина наклейки — как в файле заказчика, а не во весь лист.** В `номенк.docx`
строки названия разбиты руками, и по ним видно ширину: самая длинная —
«HDD1000GB/SSD128GB/RTX2060/PSU600W/», 35 знаков. При сборке шаблона

отступ справа у всех трёх абзацев: полезная ширина 9639 твипов, знак при кегле 9 пт
≈ 90 твипов, значит на текст оставляем 35 × 90 = 3150, отступ справа 6489. Так Word
переносит там же, где переносил заказчик.

**Номер и склад — всегда в одну строку.** Отступ справа стоит только у абзаца с
названием типа. Сначала он был у всех трёх, и «5004 Центральный склад Завод-1»
(3515 твипов жирным 12 пт при 2442 доступных) переносился на вторую строку.

**Название типа — ровно две строки и целиком.** Ширину строки даёт сам шаблон
(`line_width()`): страница минус поля минус отступ справа — 3150 твипов. Текст
раскладывается по строкам с разрывом по пробелам и по косой черте, а **кегль
подбирается**: начинаем с 9 пт из шаблона и уменьшаем по полпункта, пока всё
название не уложится в две строки (`fit_text`, пол до 5 пт). Короткие названия
остаются 9 пт, длинные мельчают. Только если не влезает и в 5 пт — режем и ставим

кегля» давала 90 твипов, а Times New Roman на этом тексте — 101: ошибка в пятую

четыре. Теперь ширина строки меряется через Pillow (он в проекте уже есть — читает

msttcorefonts или метрически совместимый Liberation Serif. Файла нет вовсе —
считаем с запасом (0,58 кегля на знак): скорее уменьшим кегль, чем получим лишнюю
строку.

Длинные названия режутся делением пополам (`_cut_to_width`), а не перебором по
знаку: на названии в тысячу знаков перебор давал десятки тысяч замеров и подвешивал
запрос на минуты.

странице. Чужие учреждения отсекаются по `registry.org_id`. Если запись одна, файл
зовётся по её инвентарному номеру («Номенклатура 1231231.docx»).

«Материал» в окне больше нет: название и номенклатура — в заголовке («Выдать: Чернила
Epson 664 · 0091220»), первым полем — **«Остаток»** (8 шт · по цене). Связку по-прежнему
держит скрытый `<select id="isSup">` — на нём стоит вся прежняя логика сохранения.

**Сотрудник, оборудование, место — набором с подсказками** (`makePick(selId)`):
в окне выдачи `isUser`, `isItem`, в карточке оборудования `f_owner`, `f_place`,
`f_parent` («За кем закреплено»). Набираешь часть ФИО, инвентарного номера, типа или
названия раздела — ниже список совпадений (все слова запроса должны встретиться),
у техники справа раздел. Стрелки и Enter, мышь, Escape закрывает подсказки, а не окно.
На фокусе показывается весь список (до 60 строк, дальше «уточните запрос»). Ушёл из
поля: пусто — выбор снят; текст совпал ровно с одним вариантом — он и выбран; иначе
в поле возвращается прежнее — текста «мимо списка» не остаётся.

Как устроено. `<select>` не удалён, а скрыт: код и дальше заполняет его `innerHTML`,
читает и ставит `.value`, слушает `change` (подстановка подразделения по сотруднику,
замок прикреплённого, характеристики для установки — всё работает как было).
Поле ввода вставлено рядом; `value` у конкретного select переопределён через
`Object.defineProperty`, чтобы программная установка сразу обновляла текст, а
`MutationObserver` ловит смену вариантов и `disabled` (режим «только просмотр»).
`sel.focus()` переводит фокус в поле — проверки при сохранении этим пользуются.
Подпись `label[for=…]` оставлена на select: её текст меняют по id (звёздочка
обязательности), поэтому фокус по клику ведётся отдельным обработчиком. Список
подсказок — `position:fixed` с пересчётом на прокрутке, окно его не обрезает.

Проверено на стенде (1440 и 820 px): «карим» → Каримов и Каримова, «карим дил» →
одна, Enter выбрал; чужой текст при уходе вернул прежнее; стёрли — выбор снят;
«новиков» и уход — выбран единственный; техника «3613» → 3 номера, стрелка+Enter
выбрали, Escape закрыл подсказки, окно осталось; установка сохранилась. Карточка:
выбор сотрудника подставил подразделение и отдел, место «каб» → 2, «Прикрепить к»
0013500 включил замок прикреплённого, программный сброс очистил поле, у другой
записи поле показало её сотрудника. Прежний сценарий «Таблицы факт» прошёл без
изменений, горизонтальной прокрутки нет.

### Модель в списании — внутри материала; карточка материала по карандашу (28.09.2026)

**Поле «Модель» в шапке окна «Списание по документам» убрано** (было сделано утром
того же дня — заказчик уточнил, как надо). Модель задаётся материалу при приходе,
и теперь она работает в окне «Куда списать» (нажатие на материал в списке акта):
подразделения, отделы и склады берутся только те, где стоит **техника моделей этого
материала** (`woScope(row)`): у самой техники — подразделение, отдел, склад; у
прикреплённой — подразделение и отдел того, к чему она прикреплена (`holderOf().root`).
Списанная техника не считается. Списки каскадом: выбрал подразделение — отделы и
склады только те, где такая техника в этом подразделении; выбрал отдел — склады ещё уже.
**Материал без модели — списки полные**, как было. Если у материала модели есть, а
техники таких моделей нет — в списках так и написано: «техники этих моделей нет».
Под заголовком окна видно, по каким моделям отобраны места.

**Карандаш в «Таблице факт» открывает карточку материала** (`dlgSup`, `openSupCard`)
вместо череды окон `prompt`. В ней: название, единица, номенклатурный номер,
стоимость, модели (список с «+» и чипами, галочка «Без модели»), примечание; внизу —
поступило / выдано / остаток / по документам; кнопки «Удалить», «Отмена», «Сохранить».
Название, единица, модели и примечание — у материала целиком. Номенклатура и цена —
у **этой строки** (связки): при смене они переписываются во всех её приходах,
выдачах и документальных списаниях, иначе остаток развалился бы на две строки. Для
этого нужны оба права — `supply.receive` и `supply.issue`, иначе эти два поля заперты.
Имя, которое уже носит другой материал, не принимается. Список моделей для прихода и
для карточки строит одна функция `supModelOptions()`; удаление вынесено в `delSupply()`.

Проверено на стенде (1440 и 820 px): в шапке списания поля модели нет; «Чернила»
(HP, Seagate) — подразделения Рудник и Энергоцех, склады 5004 и 0117; выбрали

10/2/8/10; имя «Термопаста» отклонено; сменили имя, номенклатуру 0091220, цену

остались (выдача переехала вместе со связкой), строк по-прежнему 3; «Без модели»
очистил модели. Горизонтальной прокрутки нет.

### Резерв IP-адреса с данными вручную — для виртуальных серверов (28.09.2026)

Раньше нажатие на свободный адрес спрашивало `prompt`-ом «за кем», а на резерв —
«снять резерв?». Виртуальные серверы в учёт оборудования не заводятся, и описать
такой адрес было нечем. Теперь **любой адрес открывает свою карточку** (`dlgIp`):
занятый — как раньше, с историей пингов и кнопкой «Карточка оборудования»;
**не привязанный к оборудованию** (свободный или в резерве) — ещё и с блоком
«Резерв — данные вручную»: имя / название, тип устройства (подсказки из уже
заведённых типов), ОС, где работает, ответственный (поле с подсказками, подставляет
подразделение и отдел сотрудника, если они пусты), MAC, подразделение, отдел,
примечание. Кнопка «Зарезервировать» (у существующего резерва — «Сохранить») и
«Снять резерв». Сохранённый адрес на сетке **жёлтый**, как любой резерв; подпись —
имя, иначе примечание (`resLabel`), в подсказке — имя, тип, ответственный. В
таблице адресов у резерва видны ответственный, имя (в колонке инв. номера) и тип;
строка резерва тоже открывает карточку. Подписи сетки по полям (сотрудник, тип,
имя хоста) берут ручные данные резерва. Старые резервы без данных открываются и
правятся так же — у них заполнено только примечание.

Хранение: миграция `031_ip_reserved_data.sql` — `ip_reserved.data jsonb`, поля
перечислены в `RES_FIELDS` в `app.py` (name, kind, os, host, owner, divisionId,
departmentId, mac); в состоянии они лежат прямо в объекте резерва рядом с `note`.
Сборка `2026-09-28.2` — сервер перезапущен, миграция применилась.

Проверено. База (дамп заранее: `backup/asset_it_2026-09-28_before_ipres.dump`):
круговой прогон `save_cfg` → `load_state` в одной транзакции с откатом — все восемь
полей вернулись, прежние строки целы, после отката tmp-строк 0. Стенд (1440 и
820 px): у занятого адреса ручного блока нет; свободный .77 — «Зарезервировать»,
ответственный по «хайит» подставил подразделение и отдел; после сохранения клетка

## 7. Как проверять изменения

Сборки нет, поэтому проверка — прогон настоящей страницы в headless-браузере:

```bash
# 1) синтаксис JS (JScript строг к ES5, .catch/.delete нужно временно переименовать)
cscript //Nologo //E:JScript parse-test.js

# 2) интеграционный прогон: скрипт-сценарий дописывается в копию страницы,
#    результат складывается в document.title и читается из dump-dom
chrome --headless=new --disable-gpu --window-size=1440,900 \
       --virtual-time-budget=9000 --dump-dom file:///.../test.html | grep '<title>'
```

Сценарии кликают по реальным кнопкам (`side()`, `rt()`, `card()`), поэтому ловят и
логику, и вёрстку. Обязательно проверять `overflowX` (горизонтальной прокрутки быть
не должно) и совпадение числа `<col>` / `<th>` / ячеек во всех таблицах.

Перед правкой — копия файла в отдельную папку. Предыдущие копии лежали во временном
каталоге сессии (`…\Temp\…\it-inventory.backup*.html`) и
**после перезагрузки могут пропасть** — если нужна история, копировать рядом с проектом.
